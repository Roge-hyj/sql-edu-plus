# SQL Edu 多方言原生引擎执行改造计划

> 编制时间：2026-08-12 16:40:23（北京时间，UTC+8）  
> 基线：Phase 1 Observe 已具备 sqlglot 结构 IR、AST Diff、动态造数、沙盒执行和变异证据链。  
> 本计划先作为基线提交的一部分写入仓库；执行改造从后续独立提交开始。

## 1. 目标与边界

目标是让判题链路以题目声明的 SQL 方言和数据库版本为准，在结构层统一比较、在造数和变异层使用对应的原生数据库执行，从而减少 SQLite 兼容层造成的语义偏差。

本计划不承诺任意版本、任意扩展和任意 SQL 的绝对兼容；系统必须对支持、方言边界、引擎不可用、超时和安全拒绝进行可审计分类。别名导致的重复列名与歧义列问题按当前约定暂缓，不作为本阶段改造目标。

## 2. 总体架构

```text
FastAPI / 判题 API
        |
        v
Judge Job / Sandbox Orchestrator
        |
        +-- SQLStructureIR + ASTDiff（sqlglot，按题目 dialect 解析）
        |
        +-- Fixture Planner（结构差异驱动、引擎感知）
        |
        +-- Native Engine Runner
        |     +-- MySQL 8.0
        |     +-- PostgreSQL 16
        |     +-- SQL Server 2022
        |     +-- Oracle Free/23ai（受控执行节点）
        |
        +-- Mutation Runner（同一引擎、同一 fixture、隔离事务）
        |
        +-- Result Canonicalizer + Evidence Bundle
```

## 3. 分阶段实施

### 阶段 A：方言元数据与执行契约

- 确认 `sql_dialect`、`engine_version`、时区、字符集、collation、兼容模式和资源限制均属于题目/执行配置。
- 规范方言别名映射：`postgresql -> postgres`、`mssql/sqlserver -> tsql` 等。有题目方言时严格按声明方言；无题目方言时先用 SQLGlot 通用语法解析，再由 `TOP`、`DISTINCT ON`、`::` 等高置信专属特征选择引擎；没有唯一专属特征时使用系统默认引擎。
- 定义统一执行结果：`CORRECT`、`WRONG`、`UNSUPPORTED`、`ENGINE_ERROR`、`TIMEOUT`、`SECURITY_REJECTED`。
- 为每次执行生成 `execution_id`、引擎标识、镜像 digest、fixture hash 和超时信息。

### 阶段 B：Runner 抽象与 SQLite 兼容层保留

定义稳定的异步接口：

```python
class NativeEngineRunner(Protocol):
    async def provision(self, question_meta) -> SandboxHandle: ...
    async def load_fixture(self, sandbox, fixture) -> None: ...
    async def execute(self, sandbox, sql, timeout_ms) -> QueryResult: ...
    async def reset(self, sandbox) -> None: ...
    async def destroy(self, sandbox) -> None: ...
```

- 将当前 SQLite 执行器包装为 `SqliteCompatRunner`，作为本地测试和明确兼容 fallback。
- 原生 Runner 不应改变 `generate_and_compare` 的上层判题契约。
- Runner 生命周期必须支持容器池预热、任务级 schema/database 隔离和失败清理。

### 阶段 C：Docker 原生引擎适配

优先顺序：PostgreSQL 16、MySQL 8.0、SQL Server 2022，最后接入 Oracle Free/23ai。每个适配器固定镜像版本和 digest，提供健康检查、初始化脚本、连接池和资源限制。

- MySQL：数据库级隔离、严格 SQL mode、字符集和 collation 显式设置。
- PostgreSQL：schema/role 隔离、search path 固定、时区固定；单独处理数组、JSON、`FILTER`、`SEARCH/CYCLE` 能力矩阵。
- SQL Server：database/schema 隔离、`SET ANSI_NULLS` 等会话选项显式设置，处理 `TOP/OFFSET/FETCH`。
- Oracle：只在受控节点启用；记录许可证/镜像前置条件，不可用时返回 `UNSUPPORTED_ENGINE`，禁止静默降级。

### 阶段 D：引擎感知 Fixture Planner

将现有 `dict[str, list[dict]]` 扩展为带列类型、约束、索引、种子和引擎 profile 的 Fixture 对象：

- 根据 AST Diff 生成边界、重复、NULL、ties、关联键和递归图数据。
- 将 schema preview 编译为目标引擎 DDL，保留类型精度、主键、外键、唯一约束和排序规则。
- 对 Oracle 空字符串即 NULL、PostgreSQL 类型/数组、SQL Server `BIT`/日期函数等差异提供显式策略。
- fixture 生成必须可复现：保存 seed、策略列表、约束摘要和 hash。

### 阶段 E：原生变异执行

- 结构层生成的 mutant 保持题目原始方言，不先转 SQLite。
- 标准、学生和 mutant 在同一 sandbox、同一 fixture、独立事务中执行。
- 对每个变异记录替换 SQL、执行状态、结果摘要、是否修复标准差异、耗时和错误分类。
- 变异只有在 `fixed_by_replacement=true`、知识点 ID 命中预期 KP、clause 命中该 KP 的允许子句，且不是跨多子句的复合恢复时，才计为错因定位证据。
- 若随机数据未穿透，允许按策略追加探针；最终必须报告 `NO_OBSERVABLE_COUNTEREXAMPLE`，不得把“策略触发”当作反例成功。

### 阶段 F：结果归一化与证据包

统一处理 NULL、Decimal、日期/时区、布尔值、尾随空格、浮点容差和无根级 `ORDER BY` 的无序结果。只有最终结果所在的根查询块（包括集合查询根节点）显式声明 `ORDER BY` 时才进行严格顺序比较。子查询的 `ORDER BY` 可与子查询 `LIMIT` 一起改变行集，但不能把外层结果标记为有序；嵌套子句差异和其变异必须保留在原查询块作用域。

证据包至少包含：原始 SQL、统一 IR/差异图、方言/版本、DDL 摘要、fixture hash、标准/学生/mutant 原始结果、规范化结果、超时和资源用量。

### 阶段 G：安全、资源和运维

- AST 白名单限制为题目要求的 DQL；拦截 DDL/DML、系统命令、文件读写、外部网络、扩展和链接服务器。
- 容器无 Docker socket、默认无网络、非 root、只读镜像；设置 CPU、内存、进程、临时磁盘和执行时间上限。
- 数据库账号最小权限；数据库超时和容器 watchdog 双重保护；所有失败路径清理 schema/database/container。
- 记录镜像 digest、驱动版本、数据库版本和健康检查结果，支持审计与重放。

## 4. 测试与验收门槛

1. 每个 Runner 通过连接、DDL、类型、事务回滚、超时和清理测试。
2. 每种方言建立基础 SELECT/JOIN/GROUP、相关子查询、窗口、CTE/递归 CTE、集合运算和 NULL 回归集。
3. 同一 fixture 在 SQLite fallback 与原生引擎上的差异必须分类为语义差异或兼容边界，不能静默吞掉。
4. Phase 1 结构反例、等价保持和变异修复指标分别统计，不用单一总通过率掩盖方言失败。
5. 目标验收：支持范围内的结构差异必须有可观察反例或明确 `NO_OBSERVABLE_COUNTEREXAMPLE`；方言不可用时必须返回可审计的 `UNSUPPORTED_ENGINE`。
6. 对预期非等价案例，门禁必须从完整的 per-test mutation detail 中找到 KP 和 clause 同时精确命中的单点修复；只有汇总计数或宽泛复合恢复不得通过此项。

## 5. 交付顺序与回滚

- 先提交本计划和当前实现基线。
- 后续每个 Runner、Fixture、Canonicalizer 和 API 接入使用独立小提交，避免大范围不可回滚变更。
- 保留 SQLite 兼容 Runner 用于旧内部调用和本地测试；API 显式使用 `auto/native` 时，必须进入最终解析出的原生引擎，连接未配置或引擎不可用时返回 `ENGINE_ERROR`，不得静默降级 SQLite。
- 原生 Runner 出现异常时回退为明确的 `ENGINE_ERROR/UNSUPPORTED`；不得在生产环境静默改变判题语义。

## 6. 开发环境原生引擎启动

仓库提供 `sql-edu-backend/compose.native-engines.yml`。默认启动 MySQL 8.4 和 PostgreSQL 16；SQL Server 2022 与 Oracle Free 23ai 资源占用较大，放在 `full` profile。

```bash
cd sql-edu-backend
docker compose -f compose.native-engines.yml up -d
docker compose -f compose.native-engines.yml --profile full up -d
```

本地 `.env` 可配置：

```dotenv
PARSEVAL_EXECUTION_BACKEND=auto
PARSEVAL_MYSQL_URL=mysql://root:parseval_dev_root@127.0.0.1:13306/parseval
PARSEVAL_POSTGRES_URL=postgresql://postgres:parseval_dev_root@127.0.0.1:15432/parseval
PARSEVAL_TSQL_URL=mssql://sa:Parseval_Dev_2026%21@127.0.0.1:11433/master?driver=ODBC+Driver+18+for+SQL+Server
PARSEVAL_ORACLE_URL=oracle://sys:Parseval_Dev_2026%21@127.0.0.1:11521/FREEPDB1?mode=sysdba
PARSEVAL_MYSQL_VERSION=8.4
PARSEVAL_POSTGRES_VERSION=16
PARSEVAL_TSQL_VERSION=2022
PARSEVAL_ORACLE_VERSION=23ai
```

SQL Server Python runner 除 `pyodbc` 外还需宿主机安装 Microsoft ODBC Driver 18。Compose 为各引擎设置了内部网络、CPU、内存、进程数和日志上限，仅用于开发与集成测试。Runner 使用 provisioner 凭据创建隔离区和 fixture，随后切换为仅有查询权限的临时身份执行标准、学生与 mutant SQL。生产应使用独立执行节点或预热池，固定镜像 digest，使用专用网络和秘密管理，且不得向 API 容器暴露 Docker socket。
