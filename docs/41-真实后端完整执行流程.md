这份文档不是产品目标、论文设想或测试计划，而是按照当前仓库中的真实代码，把一次 SQL 提交从进入 API 到最终返回的完整链路拆开说明。

阅读时需要区分三件事：

1. “代码具备某项能力”不等于“每次请求都会走到该能力”。例如原生 PostgreSQL runner 已经有实现，但是否实际使用还取决于方言、后端选择、连接 URL、Docker 服务和运行时配置。

### 1.2 重要的分叉

| 分支 | 经过的阶段 | 是否写 Submission | 是否更新 BKT | 是否生成学习反馈 |

“安全拦截”和“语法错误”虽然会生成面向学生的提示，但它们不是“学生知识点答错”意义上的语义判题，所以不进入语义 BKT。

## 2. API 层：一次请求先经过什么

### 2.1 应用与路由

[main.py](/home/roge/projects/sql-edu-main/sql-edu-backend/main.py:20) 创建 FastAPI 应用，挂载：

- /auth：注册、登录、当前用户、邮箱验证等；
- /ai：SQL 检查、历史提交、反馈、聊天、掌握度雷达等；
- /questions：题目列表、详情、schema 预览、题目管理和知识点相关接口；
- /：健康或基础接口；
- 可选邮件测试接口。

本次 SQL 教学主链路是 /ai/check-sql，不是 /ai/sql-hint 或 /ai/chat。

### 2.2 请求对象与输入硬门禁

SQLCheckRequest 的实际关键字段是：

~~~text
student_sql  : 1 到 32768 字符
question_id  : 整数
attempt_id   : UUID
language     : zh-CN、zh-TW 或 en
extra        : 禁止额外字段
~~~

这一步解决的是“请求形状和身份是否可信”，不是 SQL 是否正确。输入不符合模型或认证要求时，流程在业务判定前结束。

相关实现：

- [ai.py](/home/roge/projects/sql-edu-main/sql-edu-backend/routers/ai.py:1312)
- [auth.py](/home/roge/projects/sql-edu-main/sql-edu-backend/routers/auth.py:20)
- [question.py](/home/roge/projects/sql-edu-main/sql-edu-backend/routers/question.py:196)

### 2.3 进程内单飞与请求幂等

系统先用用户、题目和 attempt_id 对同一次尝试做进程内串行化，避免同一进程同时处理同一个 attempt。

真正的幂等身份是：

~~~text
(user_id, question_id, attempt_id)
~~~

同时生成请求指纹。指纹只包含规范化后的：

~~~json
{"student_sql": "...", "language": "..."}
~~~

然后计算 SHA-256：

- 同一 attempt、同一指纹：返回已有快照，idempotency_replayed=true，不会重新执行 SQL、重新更新 BKT 或再次写学习事件；
- 同一 attempt、不同指纹：返回 409 ATTEMPT_ID_REUSED；
- 快照缺失、损坏或与请求冲突：返回相应的幂等冲突错误；
- 正常请求继续进入判题。

流程末尾还会在数据库事务中再次锁定并读取 attempt，防止两个进程绕过前面的进程内锁同时提交。这个“先快照检查、最后数据库锁复核”的设计是为了让判题和学习更新具有一次性语义。

### 2.4 题目读取

题目读取提供后续所需的：

- 正确 SQL；
- 题目声明的 SQL 方言及可能的版本；
- schema 文本或结构化 schema preview；
- 题目知识点/Q-matrix；
- 任务描述和输出约束。

学生端题目详情的公共 DTO 不返回 correct_sql；教师题目 DTO 才可能带答案。题目相关逻辑在 [question.py](/home/roge/projects/sql-edu-main/sql-edu-backend/routers/question.py:196)。

## 3. 第一条分支：安全策略、方言和“能 parse”之间的区别

### 3.1 第一轮安全门禁

student_sql_safety_error 在 [ai.py](/home/roge/projects/sql-edu-main/sql-edu-backend/routers/ai.py:1312) 附近调用原生 SQL 安全检查。安全策略检查的不是答案是否正确，而是这段 SQL 是否有资格被送进执行器。

会被拦截的典型类别包括：

- 多语句；
- INSERT、UPDATE、DELETE、MERGE、DROP、ALTER、CREATE 等 DML/DDL；
- 修改数据库或产生副作用的语句；
- 外部文件、系统对象、危险函数或不可信函数；
- 不受控的系统表访问；
- 无界或危险的 generate_series；
- 其他 runner 不允许的高风险扩展。

#### “多语句直接退出”是什么意思

例如一次请求中包含：

~~~sql
SELECT * FROM members;
DROP TABLE members;
~~~

即使第一句可以 parse，整体请求也不是一个可接受的只读查询。安全门禁会在执行前拒绝它；系统不会执行第一句再“顺便”判断第二句，也不会让 parse 成功替代安全授权。

#### “能 parse 不自动获得执行资格”是什么意思

sqlglot.parse 或方言解析成功，只表示语法树可以构造出来。之后仍需满足：

1. 必须是允许的单条只读查询；
2. 学生方言和标准方言必须能确定；
3. 表和列引用必须通过题目 schema/catalog 授权；
4. 必须能选择兼容 runner 或原生 runner；
5. 原生 runner 还必须能建立隔离、设置超时并完成安全执行；
6. 执行结果必须能形成足够证据。

所以 parse 成功但安全拒绝、parse 成功但 runner 未配置、parse 成功但 schema 未授权、parse 成功但证据不足，都是合法且必要的失败路径，不应被报告为“学生 SQL 正确”。

### 3.2 schema/catalog-qualified table 的特殊处理

当前 API 第一轮门禁通常还没有完整题目 catalog。因此像：

~~~sql
SELECT m.firstname
FROM cd.members AS m
~~~

这样的 cd.members 不能简单地因为“带点号”就一律拒绝。代码对“可能是题目允许的 schema/catalog 限定名”保留一个延迟授权分支，交给 Phase1 在拿到题目 catalog 后判断。

Phase1 的实际规则是：

- 标准 SQL 或题目 catalog 证明 cd.members 合法：可以建立可信 namespace 映射，再进入隔离 fixture；
- 题目没有证明该 namespace：安全拒绝；
- 未知或禁止 namespace：安全拒绝；
- 通过 SQLite compatibility rehearsal 时，限定名会被安全地重写到隔离的物理 fixture；
- 原生 PostgreSQL 时保留目标方言语义，在随机 schema/权限隔离中执行。

因此，SQLite rehearsal 可以证明“重写后的兼容语义在给定世界中产生了什么结果”，但不能冒充原生 PostgreSQL 执行证明。

### 3.3 安全拦截分支的输出和持久化

安全分支不会进入 Phase1、Phase2，也不会更新语义 BKT。它会：

- 创建 Submission；
- 创建教学审计记录；
- 记录 SAFETY_BLOCKED Phase3 行为事件；
- 生成聊天/反馈快照；
- 选择固定的 SYSTEM_NOTICE、L1 教学动作；
- 返回 judge_status=WRONG、is_safety_blocked=true；
- 不把安全策略细节或内部答案泄露给学生。

这是“请求不合格”，不是“某个 SQL 知识点掌握失败”。

### 3.4 方言解析分支

方言解析在 [sql_dialect_resolver.py:320](/home/roge/projects/sql-edu-main/sql-edu-backend/core/sql_dialect_resolver.py:320) 一带完成。方言来源优先级由显式题目/请求声明、可检测方言和默认配置共同决定，并会处理冲突、未知方言和版本信息。

可能的结果包括：

- RESOLVED：两侧可以在同一教学方言语境中比较；
- 方言冲突；
- 学生语法错误；
- 标准 SQL 语法错误；
- 方言不支持。

学生 SQL parse 失败时进入语法错误分支：

- 标准 SQL parse 失败属于平台/题目配置问题；
- 学生 SQL parse 失败则生成本地化、答案无关的语法反馈；
- 选择固定 SYNTAX_FEEDBACK L1；
- 写 Submission、审计、SYNTAX_ERROR 行为事件和反馈快照；
- 不创建 SkillObservation，不更新 BKT；
- 返回 WRONG，但不把语法错误冒充成结构知识点归因。

平台错误、方言不支持、runner 失败和超时的处理不同：通常不写 Submission，不写学习事件，也不生成学生反馈，而是返回 422 或 503 的平台错误。

## 4. Phase1-1：输入门禁与解析到底做了什么

这一小步的目的不是判断等价性，而是把后续可用的“比较对象”准备好。

### 4.1 schema 输入解析

[parseval_data_generator.py:432](/home/roge/projects/sql-edu-main/sql-edu-backend/core/parseval_data_generator.py:432) 会解析题目 schema 文本或结构化预览，识别：

- 表；
- 列；
- 数据类型；
- 可空性；
- 主键；
- 唯一约束；
- 外键及关系；
- bridge/fanout 等关系元数据；
- 部分题目生成数据所需的统计或关系信息。

对格式化 schema 会进行字段级解析；旧式紧凑 schema 仍保留兼容回退。数字开头的标识符会做有限修复；某些双引号标识符会做窄范围兼容处理，但这不等于放开任意 SQL。

### 4.2 两侧 SQL parse

标准 SQL 和学生 SQL 都要按已解析方言构造 AST。这里关注的是：

- 是否为一条查询；
- 根查询结构；
- projection；
- FROM、JOIN、WHERE；
- GROUP BY、HAVING；
- WINDOW、QUALIFY；
- ORDER BY、LIMIT/OFFSET；
- 子查询、CTE、set operation；
- CASE、NULL、函数和表达式；
- 表/列引用是否能在 catalog 中解析。

仅仅得到 AST 不会直接判定正确；AST 只是 Phase1 的结构证据来源。

### 4.3 执行后端选择

代码支持以下几类后端意图：

| 配置/方言 | 实际后端意图 |
|---|---|
| sqlite compatibility | 将安全且受支持的查询转成 SQLite 兼容语义做 rehearsal |
| MySQL | 原生 MySQL runner |
| PostgreSQL | 原生 PostgreSQL runner |
| T-SQL | 原生 SQL Server runner |
| Oracle | 原生 Oracle runner |
| auto | 按目标方言和可用配置选择 |

配置位置：[settings/config.py:19](/home/roge/projects/sql-edu-main/sql-edu-backend/settings/config.py:19)。

代码默认值是：

~~~text
PARSEVAL_EXECUTION_BACKEND=auto
PARSEVAL_DEFAULT_DIALECT=mysql
native MySQL/PostgreSQL URL 默认为空
native worker mode=process
native worker start method=spawn
native max concurrency=2
native queue=8
native memory limit=2048 MB
native CPU limit=50 秒
~~~

因此“仓库中有 Docker”与“当前请求已经使用原生 PostgreSQL”是两件事。必须同时确认：

1. PostgreSQL 容器正在运行；
2. PARSEVAL_POSTGRES_URL 指向该容器；
3. 目标题目/请求解析为 PostgreSQL；
4. backend 选择没有被强制为 SQLite；
5. runner 能连接并创建隔离 schema/角色；
6. 该次观测的 backend metadata 明确记录为 PostgreSQL。

对应实现：[native_engine_runner.py:195](/home/roge/projects/sql-edu-main/sql-edu-backend/core/native_engine_runner.py:195)。

### 4.4 backend 缺口的正确表达

如果声明了 PostgreSQL，但 URL 没配置或原生 runner 不可用，不能静默降级后声称“PostgreSQL 已验证”。直接 helper 会产生 ENGINE_GAP/EXECUTION_BACKEND_REQUIRED 一类结果；API 则应返回平台错误或 UNDECIDED，具体取决于调用层的错误映射。

## 5. Phase1-2：SQLStructureIR、Query Block 与作用域图

这是最容易被表格混淆的一部分。当前代码中有两条相关但不完全相同的结构路径：

1. SQLStructureIR：用于错误归因辅助路径，当前只在 Phase1 判定为 WRONG 后被调用；
2. scope_metadata / ScopedQueryGraph：用于把 AST 差异绑定到查询块并服务 Phase2 诊断。

它们不是同一个对象，也不是“SQLStructureIR 自动生成了 scope graph”。

### 5.1 SQLStructureIR 是什么

SQLStructureIR 是把单条 SQL AST 提炼成结构特征的中间表示，类定义在 [ast_schema.py:459](/home/roge/projects/sql-edu-main/sql-edu-backend/core/ast_schema.py:459)。

它可以记录或派生出：

- projection；
- DISTINCT；
- WHERE；
- JOIN；
- GROUP BY；
- HAVING；
- ORDER BY；
- LIMIT/OFFSET；
- subqueries；
- CTE；
- set operation；
- CASE；
- window；
- predicate/logic tree；
- aggregate；
- expression；
- table reference；
- named window；
- DISTINCT ON；
- QUALIFY；
- grouping sets、ROLLUP、CUBE；
- recursive decorations；
- LATERAL；
- limit options；
- hierarchy、pivot、sample、only 等扩展信息。

它回答的问题是：

> 这棵 AST 具有什么结构特征，标准 SQL 和学生 SQL 在哪些结构能力上可能不一致？

它不是执行数据库，不是等价性证明器，也不是主流程中的唯一结构表示。

### 5.2 SQLStructureIR 在当前真实主链路中的位置

当前真实调用关系是：

~~~text
Phase1 得出 WRONG
  -> error_weights_from_observation
  -> 从 standard/student AST 提取 features
  -> SQLStructureIR.from_ast
  -> _structural_kps
  -> 得到结构相关知识点集合
  -> 辅助错误归因/解释性证据
~~~

实现入口见 [error_attribution.py:1408](/home/roge/projects/sql-edu-main/sql-edu-backend/core/error_attribution.py:1408)。

重要限制：

- CORRECT 路径不调用这条归因辅助路径；
- safety、syntax、platform、timeout、UNDECIDED 不调用；
- Phase2 的 diagnose_record 会明确删除/不消费 attribution_result；
- Phase2 主要消费 Phase1 的 SandboxRun、AST diff、mutation、witness、scope metadata；
- 所以不能把 SQLStructureIR 写成“Phase2 主诊断图”。

内部 observation 还会去掉 _ir 等内部对象，避免把实现细节直接序列化给外部。

### 5.3 Query block 是什么

一个 Query Block 是一块独立的 SELECT 语义范围。不是每一个括号都一定独立成 block，但常见结构如下：

~~~text
ROOT
├── CTE
├── DERIVED       FROM (SELECT ...)
├── SUBQUERY      WHERE/SELECT 中的子查询
└── SET_BRANCH    UNION/INTERSECT/EXCEPT 的一个 SELECT 分支
~~~

“作用域”在这里不是数据库 schema 名称 cd。它表示：

> 某个 SELECT 条件、表引用、排序或聚合，究竟属于哪一块 SELECT。

例如外层 WHERE 与 EXISTS 内层 WHERE 都可能出现，但它们属于不同 query block；内层如果引用外层列，还存在相关依赖。

### 5.4 scope_id 与 conceptual_scope_id

每一侧 SQL 都会有自己的 scope 标识：

~~~text
standard:root
student:root
standard:root/cte:recent
student:root/cte:recent
~~~

scope_id 是侧别感知的定位 ID。它回答：

> 在 standard 或 student 这一侧，当前结构节点在哪个查询块？

只有当标准和学生块在结构路径、块类型等方面可靠对应时，才生成 conceptual_scope_id。它回答：

> 这两个侧别的查询块，是否可以认为是在比较同一个概念位置？

因此：

- standard:root 和 student:root 可以各自存在；
- 它们只有在可靠配对后才有共同 conceptual_scope_id；
- 一个标准 CTE 找不到学生对应块时，不应该强行把它和学生根查询合并；
- 配不上只说明定位信息不足，不说明学生一定写错。

### 5.5 parent_edges 和 composition edges

父子/组合边描述 query block 之间如何组织：

| 边 | 真实语义 |
|---|---|
| PARENT | 词法或结构上的父子关系 |
| CTE_FEEDS | CTE 为外层查询提供数据 |
| DERIVED_FEEDS | 派生表为外层查询提供数据 |
| SUBQUERY_OF | 子查询属于哪个外层查询 |
| CORRELATED_TO | 内层查询引用外层字段，存在相关依赖 |
| SET_MEMBER_OF | 某个 SELECT 分支属于 UNION/INTERSECT/EXCEPT |
| LATERAL_TO | LATERAL 查询依赖左侧来源或外层可见来源 |

例如：

~~~text
ROOT
├── CTE_FEEDS -> CTE
├── DERIVED_FEEDS -> DERIVED
├── SUBQUERY_OF -> SUBQUERY
├── CORRELATED_TO -> 外层字段依赖
└── SET_MEMBER_OF -> UNION 分支
~~~

#### “LATERAL 派生查询可以依赖外层或左侧来源”是什么意思

普通派生表通常只能使用自己的 FROM 范围；LATERAL 明确允许该派生查询读取它左边已经出现的来源。例如概念上：

~~~sql
FROM members AS m
JOIN LATERAL (
  SELECT ...
  WHERE ... = m.id
) AS x ON true
~~~

内层派生查询依赖外层/左侧的 m.id，所以 graph 需要记录 LATERAL_TO 或相关依赖。它不是把两个 SELECT 当成一层，也不是说所有子查询都能引用外层列。

### 5.6 PARTIAL/unscoped 的准确含义

当 query block 无法可靠配对或某条差异无法绑定到确定的 query block 时，scope metadata/ScopedQueryGraph 会标出：

- PARTIAL：图或配对结果只完成了一部分，仍有缺失/不确定；
- unscoped:<diff_id>：这条差异存在，但没有可靠的 scope 定位。

它表达的是：

> 系统缺少足够的结构定位信息，暂时不能把差异归属到某一个确定查询块。

它不表达：

> 学生一定写错、差异一定是根因、应该更新 BKT。

Phase2 会将这类差异保留为 unresolved/unscoped 证据，不能因为定位缺失而强行归因。

## 6. Phase1-3：AST diff、稳定 diff_id 与结构差异

### 6.1 AST diff 做什么

extract_ast_diffs 将标准 AST 与学生 AST 做结构比较，输出差异节点。每条差异通常包含：

- clause；
- diff_type；
- 目标 table/column；
- 标准节点；
- 学生节点；
- 关联知识点；
- 严重度；
- extra metadata；
- scope 或后续 scope binding。

可识别的差异族包括：

- SELECT/projection；
- WHERE；
- JOIN 类型和 ON 条件；
- GROUP BY；
- HAVING；
- 聚合；
- DISTINCT；
- CASE；
- window；
- ORDER BY；
- LIMIT/OFFSET；
- subquery/EXISTS/IN；
- correlated query；
- CTE；
- set operation；
- NULL；
- LIKE/正则及其他表达式。

这一步找到的是“结构上不同”，不是直接宣判“结果一定不同”。

### 6.2 稳定 diff_id 是什么

稳定 diff_id 是同一结构差异跨证据层传递时的关联键。系统根据差异的语义内容生成哈希，通常包含：

- clause；
- diff_type；
- 目标 table/column；
- 关联知识点；
- 标准节点序列化；
- 学生节点序列化；
- extra 信息。

格式类似：

~~~text
diff_0123456789abcdef
~~~

它不是数组下标，也不依赖差异在列表中的顺序。这样一条“将 > 改成 >=”的差异可以同时出现在：

~~~text
AST diff
  -> DistinguishingObligation
  -> witness world
  -> mutation
  -> witness evidence
  -> Phase2 EvidenceDiff
  -> Phase3 规则映射
~~~

“差异绑定及稳定 diff_id”具体就是：

1. 先确定差异属于哪个 standard/student scope；
2. 只有可靠配对时绑定共同 conceptual scope；
3. 把 clause、差异类型、节点和目标信息生成稳定 ID；
4. 后续所有证据引用这个 ID；
5. 若 scope 无法确定，保留 diff_id，但 scope 绑定为 partial/unscoped。

### 6.3 一个简单例子

~~~sql
-- 标准
WHERE credits > 3

-- 学生
WHERE credits >= 3
~~~

系统可以记录：

~~~text
scope: root（若两侧根块可靠配对）
stage: ROW_FILTER
clause: WHERE
diff_type: comparison_strictness
standard node: >
student node: >=
diff_id: diff_<稳定哈希>
~~~

然后造数策略可能尝试生成 credits=3 的边界值。如果标准结果不包含、学生结果包含，才获得运行证据。只有结构差异而没有足够运行证据时，不能把它写成已证明不等价。

## 7. Phase1-4：差异如何变成造数、变异和消融证据

### 7.1 从 diff 编译 obligation

compile_obligations 将安全支持的 AST 差异编译成 DistinguishingObligation。一个 obligation 不是一条任意 SQL，而是一个证据目标，例如：

~~~text
在某个最小数据世界中，让标准和学生在该差异点产生不同结果。
~~~

如果差异没有安全的模板或无法构造约束，obligation 可以被跳过或标为无法物化；不会强行生成伪证据。

### 7.2 WitnessPlanner 与约束账本

WitnessPlanner 最多规划有限数量的测试世界，当前上限为 8 个世界。每个 WitnessWorld 记录：

- 关联 obligation/diff ID；
- 约束；
- 最小行数；
- 数据库/fixture；
- 规划诊断；
- 执行结果。

ConstraintLedger 负责检测不同 obligation 对同一单元格的冲突：

- 能合并就合并；
- 发生冲突就拆分成不同 world；
- 不覆盖原约束制造“看似满足”的假证据。

这正是“造数”和“消融”能够追溯的基础。

### 7.4 约束物化和记录

生成每个 world 时：

1. 根据 schema 建立隔离 fixture；

5. 记录写入审计、规划诊断和约束应用结果；
6. 若约束无法物化，记录 declared_constraint_not_materialized 等诊断；

- 原差异/diff_id；
- 替换前后结构；
- 是否固定了目标差异；
- 是否等价；
- 执行结果或跳过原因。

“消融”在这里的含义是有控制地去掉/替换一个结构因素，观察标准、学生或候选修复的行为变化；不是随意改写 SQL。

## 8. Phase1-5：如何执行 SQLite compatibility 与原生 runner

### 8.1 物理 fixture 与可信 namespace

prepare_executable_sql_pair 会根据标准 AST 和题目 catalog 建立可信 namespace map：

- 题目 catalog/标准 SQL 明确允许的 cd.members、cd.bookings 等限定名可以授权；
- 未知 namespace 或禁用 namespace 不允许进入执行；
- 表名映射到隔离 fixture；
- 学生 SQL 不能凭空声明题目之外的表。

这是解决 schema-qualified table 的安全授权，而不是放开任意点号引用。

### 8.2 SQLite compatibility rehearsal

兼容模式会将目标 SQL 在安全范围内转译为 SQLite 可运行形式，并在隔离数据库中执行。它适合：

- 验证结构差异是否能在一个具体小世界中造成结果差异；
- 开发和回归测试；
- 没有原生数据库时的 rehearsal。

它不能证明：

- PostgreSQL 特有类型/函数/NULL/排序语义全部相同；
- PostgreSQL 的 schema、权限、planner 行为；
- MySQL、SQL Server、Oracle 的全部方言语义。

所以观测证据必须标明 backend；SQLite 结果不能被包装成 PostgreSQL 原生证明。

### 8.3 原生 MySQL

MySQL runner 会创建隔离数据库或临时数据库、配置只读用户和版本/标识符 profile，执行后清理。当前是否进入它取决于 MySQL URL 和 backend 选择，不由“能识别 MySQL”自动决定。

### 8.4 原生 PostgreSQL

PostgreSQL runner 的隔离思路是：

1. 连接目标 PostgreSQL；
2. 创建随机 schema；
3. 创建受限角色/reader；
4. 设置 search_path；
5. 授予必要权限；
6. 在事务范围内创建 fixture、写入数据并执行；
7. 每条查询使用 savepoint；
8. 设置查询超时和结果上限；
9. 回滚事务并清理临时对象/角色。

实现见 [native_engine_runner.py:195](/home/roge/projects/sql-edu-main/sql-edu-backend/core/native_engine_runner.py:195) 与 [native_query_safety.py:384](/home/roge/projects/sql-edu-main/sql-edu-backend/core/native_query_safety.py:384)。

PostgreSQL 的“完整路由通过”应同时满足：

- cd.members 这类题目限定名能被 catalog 授权；
- 原生 URL 真正配置；
- 请求 metadata 记录 backend=postgres；
- 原生执行成功；
- LEFT JOIN、CASE 等证据在 PostgreSQL runner 真实产生；
- 不是仅凭 SQLite compatibility 结果得出结论。

### 8.5 其他 native runner

T-SQL runner 会处理临时数据库、确定性设置、用户和清理；Oracle runner 会处理 owner/reader 用户、授权和 current schema。两者同样是条件性能力：有代码不等于当前环境已连接并通过每个方言的全量证据。

### 8.6 native safety 的第二轮校验

SQL 在 namespace 重写后还会再次执行 native safety 校验。PostgreSQL 的 generate_series 只允许特定的有界、字面量日期范围（当前上限为 366 天）；不符合约束的用法会被拒绝或进入不确定分支。

### 8.7 执行比较规则

每个候选 world 中先执行标准 SQL，再执行学生 SQL：

- 根查询有 ORDER BY：比较列和有序行；
- 根查询无 ORDER BY：比较列和多重集合（Counter/multiset），不把任意返回顺序误判为语义差异；
- native 结果有行数和大小上限；
- 每个 world 有独立的执行/错误/清理记录。

系统选择优先级一般是：

1. 已执行且能区分标准/学生的 pair-distinguished world；
2. 能区分目标 obligation 的 world；
3. 递归相关 world；
4. set operation world；
5. 兼容复合 world；
6. 没有可执行 world 时报告 engine gap，而不是猜。

如果 mutation 被禁用，系统会在可行时重放选中的 world 进行替换验证。

## 9. Phase1-6：证据如何形成最终判定

### 9.1 witness evidence

attach_witness_evidence 为每个 obligation 记录：

- 约束是否成功应用；
- 标准/学生是否都成功执行；
- 两侧结果是否真的不同；
- 差异是否与该 obligation 原子对应；
- 是否完成因果验证；
- 关联 mutation ID；
- world/backend/fixture 信息。

### 9.2 Phase1 verdict

最终判定的大致规则是：

| 条件 | Phase1 结果 |
|---|---|
| 标准/学生在已执行 world 中结果不同 | SUPPORTED / NOT_EQUIVALENT |
| 没有 AST diff，或有 diff 但 bounded 检查未找到反例 | SUPPORTED / NO_COUNTEREXAMPLE_FOUND |
| 落在语义边界、方言边界或结果不足 | SEMANTIC_BOUNDARY / UNDECIDED |
| 已知但没有足够可执行证据 | KNOWN_GAP / UNDECIDED |

### 9.3 API 的 authoritative decision

authoritative_phase1_decision 进一步把 Phase1 结果映射为 API 可继续处理的三种状态：

- CORRECT：必须是已执行、无反例、受支持、无语义边界/保护性 guard；
- WRONG：必须有可教学的 NOT_EQUIVALENT 证据；
- UNDECIDED：其余所有情况。

API 对 UNDECIDED 直接返回 JUDGE_UNDECIDED（HTTP 422），不进入 Phase2/Phase3，不给学生一个伪精确的错误归因。

这就是当前系统最值得肯定的安全边界：

> 当系统不能证明足够多时，它通常输出 UNDECIDED、INPUT_GAP、ENGINE_GAP，或在 Phase3 跳过 BKT，而不是把系统缺陷误诊成学生知识错误。

### 10.4 “按路径找到最上游错误点”

Phase2 会先把候选按照教学阶段和证据强度排序，再处理依赖：

1. 先找较早阶段的候选；
2. 如果一个早期错误能解释后续现象，就抑制后续症状；
3. 强因果证据 CAUSAL_VERIFIED 或修复证据 REPAIR_VERIFIED 才有资格作为 primary；
4. 可以保留 secondary；
5. suppressed 表示存在但被上游原因覆盖；
6. unresolved 表示证据或定位不足；
7. 最终最多输出一个主要聚焦点和有限的次要点。

例如 JOIN 造成 fanout，随后聚合数量变大：若 JOIN 的 witness/repair 证据足够，JOIN 会排在聚合症状之前；系统不会同时把所有下游数字异常都当成独立知识缺陷。

但“最上游”不是数学上的唯一因果真相，而是基于当前 evidence graph 和教学阶段顺序的最早可证实节点。

### 10.5 witness 行证据与叙事

Phase2 的 witness 提取受严格上限约束，通常最多取有限行/单元格（当前常见上限为 6 行、8 个单元格）。如果没有有效物理行，就只能给 output-level 证据，不能伪造具体样本行。

确定性叙事有三个槽：

1. student_behavior：描述学生实际写了什么结构；
2. conflict_and_witness：说明在哪个有限数据世界中与任务要求产生冲突；
3. guidance_question：用启发式问题引导学生下一步思考。

### 10.6 三种 Phase2 结果

| 结果 | 意义 |
|---|---|
| INCORRECT | Phase1 已有可证实差异，Phase2 找到可教学候选 |
| CORRECT/OPERATIONALLY_ACCEPTED | 当前有界检查接受；不宣称全局数学等价 |
| UNDECIDED/UNRESOLVED | 有差异或边界，但无法可靠定位或形成足够因果证据 |

API 的主入口只会在 authoritative Phase1 为 CORRECT/WRONG 时进入后续阶段；Phase2 独立函数可以表达 undecided，但不应绕过 API 门禁。

3. 候选为 primary；
4. 证据强度是 CAUSAL_VERIFIED 或 REPAIR_VERIFIED；
5. rule/stage/candidate 有效；
6. 该规则有精确的 rule → atomic skill 映射；
7. 不是 partial、suppressed、unresolved 或 unscoped-only。

以下情况会稳定跳过 BKT：

- EXISTS 只被识别为差异但没有安全 atomic mapping；
- 窗口函数结构复杂、无法对应一个原子技能；
- UNION/INTERSECT/EXCEPT 尚未安全映射；
- CASE 只有结构差异但证据不够；
- scope 不完整；
- 只有弱 output difference；
- 只有系统/方言/执行问题；
- Phase2 结论不稳定。

这不是遗漏，而是防止把系统不懂的内容写成学生能力缺陷。

### 11.4 当前明确的 rule → skill 例子

~~~text
S1_MISSING_BRIDGE       -> join.bridge_path
S1_CARTESIAN_PRODUCT    -> join.constraint
S1_OUTER_JOIN_MISUSE    -> join.outer_preservation
S1_SUBQUERY_CARDINALITY -> subquery.cardinality
S2_BOUNDARY             -> filter.boundary
S2_BOOLEAN_LOGIC        -> filter.boolean_logic
S2_NULL_LOGIC           -> null.three_valued_logic
~~~

完整映射以代码 taxonomy 为准；不能确认时必须跳过，而不是靠字符串相似度猜 skill。

### 11.5 历史窗口与衰减

Phase3 使用最近一段历史（当前通常取最近 10 个语义/行为事件），并处理：

- 超过约 30 分钟的 idle reset；
- recurrence decay 约 0.8；
- failure streak 上限 3；
- recent hint ratio；
- recent unassisted success。

当前“最近无辅助成功”因提交后辅助元数据仍受限，存在保守硬编码为 0 的情况，不能写成已完整观测。

### 11.6 支持需求权重与 L1/L2/L3/L4

优先级调度权重大致为：

~~~text
impact             0.30
recurrence         0.25
mastery deficit    0.20
question alignment 0.15
evidence           0.10
~~~

primary/FDP 优先于 secondary，最多选择一个 secondary。当前是确定性的加权调度器，不是 A* 或全局最优规划器。

支持需求分数大致由：

~~~text
mastery deficit             0.35
failure streak              0.30
hint ratio                  0.10
behavior                    0.10
recent unassisted success  -0.15
~~~

并据阈值得到支架级别：

~~~text
< 0.25  -> L1
< 0.50  -> L2
< 0.75  -> L3
否则    -> L4
~~~

这里的 L1/L2/L3/L4 是支架深度，不是“错误严重程度”。

### 11.7 prepare 与 apply 的区别

prepare_phase3_attempt 只计算计划，不写数据库。它可以把当前失败临时加入 provisional history，以便本次教学选择反映刚刚发生的错误。

最终持久化在 Submission 写入后的嵌套 savepoint 中执行：

- repository 锁定 user/submission/state；
- 验证所有权、结果、hint level、source、provenance；
- 用唯一 event ID 做幂等；
- 更新 BKT posterior/next prior；
- 写不可变 SkillObservation；
- 单独写 behavior event。

若学习更新失败，只回滚学习 savepoint，保留 Submission、反馈和聊天快照，并返回 DEGRADED_NO_LEARNING_UPDATE。这样不会因为一次 BKT 数据库问题抹掉学生本次提交。

### 11.8 当前 BKT 的状态

BKT 参数有版本并分别维护 posterior/next prior，默认近似为：

~~~text
P(L0)=0.20
slip=0.10
guess=0.20
transition=0.10
~~~

状态键是：

~~~text
(user_id, taxonomy_version, skill_id)
~~~

观察事件不可变，行为事件另存。系统当前仍应标记 UNCALIBRATED_MVP：工程闭环存在，但教学效果和参数阈值尚未由真实学生数据离线校准证明。

## 12. Phase4：根据支架级别选择什么教学动作

Phase4 的入口是 [teaching_action.py:403](/home/roge/projects/sql-edu-main/sql-edu-backend/core/teaching_action.py:403) 的 select_teaching_actions。

### 12.1 正确提交

正确时选择固定 acceptance 动作，L1：

- 确认任务完成；
- 可以给出下一步反思；
- 不泄露标准 SQL。

### 12.2 错误提交的 adaptive 条件

只有当以下信息准确对齐时，才启用针对性支架：

- package verdict 与 expected verdict 一致；
- selected candidate 存在；
- candidate 的 rule、stage、logical path 与 Phase3 计划相符；
- 诊断不是 unresolved/unscoped-only；
- 内部证据 lineage 完整。

否则回退到非自适应 L1 Socratic 动作，而不是使用可能指错方向的高层支架。

### 12.3 L1/L2/L3/L4 的教学具体程度

| 级别 | 允许的内部教学信息 | 学生可见风格 |
|---|---|---|
| L1 | 只提示方向/自检问题 | 点到为止的苏格拉底问题 |
| L2 | 加入学生当前结构行为 | 指出应检查哪类结构，但不写修复 SQL |
| L3 | 加入有限冲突/witness 事实 | 具体说明哪类行/条件造成差异，仍不泄露答案 |
| L4 | 加入规则级修复反思和步骤 | 更具体地指导检查顺序和局部修复思路，仍不输出标准 SQL |

所有级别都要求启发式表达，不能直接把正确 SQL 或可机械复制的完整答案交给学生。

### 12.4 fail-closed

如果教学动作选择异常，degrade_teaching_action 会退回单个 L1 SYSTEM_NOTICE，保留内部 lineage；紧急渲染器独立于主动作列表，避免异常时产生空反馈或答案泄露。

## 13. Phase5：LLM 在哪里接入，能做什么，不能做什么

### 13.1 LLM 不是默认必经

LLM 接入在 [llm_teaching.py:882](/home/roge/projects/sql-edu-main/sql-edu-backend/core/llm_teaching.py:882)，是有边界的 provider adapter。

代码默认：

~~~text
LLM_TEACHING_ENABLED=False
phase2/phase5 开关存在
timeout=8 秒
max output=1200
max input=48 KB
~~~

llm_enabled(stage) 还要求：

- 全局开关打开；
- 对应阶段开关打开；
- API key 存在；
- model 存在。

因此“系统代码补齐了 LLM”与“当前运行实例这次请求确实调用了 LLM”仍然要看 effective .env 和 provider 配置。

CC Switch 可以在启动时只读加载 provider 配置；配置入口相关设置在 [settings/config.py:19](/home/roge/projects/sql-edu-main/sql-edu-backend/settings/config.py:19)。不能只因为 CC Switch 数据库中有 provider，就断言当前后端已成功调用它。

### 13.2 Phase2 LLM reviewer

Phase2 LLM 的内部输入可以包含：

- 任务描述；
- schema；
- standard/reference SQL；
- student SQL；
- Phase1 摘要；
- 确定性 diagnostic package；
- 有界 witness/mutation/attribution；
- 允许引用的 diff/rule/candidate ID。

这个 standard SQL 只在服务端 reviewer 输入中使用，不能返回给学生。

LLM 的权限受到限制：

- 只能使用已批准的 evidence；
- 只能引用存在的 ID；
- 不能凭空增加 skill 或 witness；
- 不能改变 Phase1 的 authoritative verdict；
- 不能改变证据强度；
- 只能在已有候选中排序，或改写叙事；
- 输出必须是受约束的 JSON；
- malformed JSON、provider 错误、超时都会回退确定性诊断；
- 输出中出现 SQL-shaped 文本会被限制/拒绝。

它的角色是“证据范围内的复核和语言组织”，不是让 LLM 重新决定数据库等价性。

### 13.3 Phase5 LLM 教学语言

Phase5 只接收已经批准的、可编辑的教学动作文本。固定的 ACCEPTANCE、SYSTEM_NOTICE、SOCRATIC 等不可编辑内容会原样保留。

LLM 只能返回允许的 segment/action ID 及其改写内容，并接受：

- action ID 校验；
- 相似度阈值；
- 最大长度；
- 禁止 SQL/分号/答案形状；
- 失败回退确定性文案。

所以 LLM 能让反馈更自然、启发性更强，但不能借此获得标准 SQL 或绕过“不泄露答案”的安全边界。

### 13.4 /ai/chat 不是 Phase5

当前 /ai/chat 是基于最新提交的本地固定 Socratic 消息接口，不等同于 /ai/check-sql 中的 Phase5 LLM 教学生成链路。/ai/sql-hint 也是已经退役的静态提示响应，不应拿来证明五阶段链路已调用 LLM。

## 14. 最终持久化与公共响应

### 14.1 最终事务

在 Phase1 到 Phase5 生成内部结果后，主流程会：

1. 再次锁定用户和 attempt；
2. 重查幂等快照；
3. 确认仍是本次唯一尝试；
4. 必要时重新计算 Phase3 plan，避免期间状态陈旧；
5. 写 Submission；
6. 写 submission teaching audit；
7. 应用 Phase3 BKT/SkillObservation/behavior event；
8. 写聊天/反馈快照；
9. 保存审计和内部 lineage；
10. 返回公共 DTO。

### 14.2 对学生隐藏的内容

公共响应不会直接返回：

- 原始 SandboxRun；
- 全部内部 error attribution；
- standard/reference SQL；
- 完整 diagnostic package；
- raw witness 数据库；
- 内部 Q-matrix；
- 规则、skill、candidate、witness 的全部细节。

响应保留面向产品的字段，例如：

- is_correct；
- hint；
- submission_id；
- attempt_id；
- idempotency_replayed；
- error_message；
- judge_status；
- 安全拦截标志；
- phase3_learning；
- teaching_support；
- 兼容保留字段。

当前 lambda_t 仍为 None。

### 14.3 教学反馈渲染

render_student_feedback 会：

- 为 segment 加标签；
- 限制总长度（当前约 16 KB）；
- 生成内容 hash；
- 设置 answer_revealed=false；
- 输出推荐/实际 delivered level、策略版本和状态；
- 不把 rule/skill/candidate/witness/Q-matrix 塞进学生可见的 teaching_support。

## 16. 当前真实能力盘点

### 16.1 已真实具备

| 能力 | 具体实现 |
|---|---|
| 输入安全 | Pydantic 长度/字段门禁、认证、attempt 幂等和单飞 |
| 单条只读保护 | 多语句、DML/DDL、副作用、危险函数/对象等安全拦截 |
| 方言感知 | 能解析并区分 MySQL/PostgreSQL/T-SQL/Oracle 等目标 |
| schema 感知 | 结构化 catalog、类型、关系、键、可空性和限定名授权 |
| AST 结构比较 | 多类 SELECT/WHERE/JOIN/GROUP/HAVING/window/set/subquery 差异 |
| 稳定关联 | diff_id 跨 obligation、world、mutation、Phase2 传递 |
| 有界造数 | 多类边界、NULL、JOIN、聚合、CASE、窗口、集合等 witness |
| 约束安全 | ConstraintLedger 检测冲突并拆分 world |
| 执行隔离 | SQLite compatibility，以及有配置时的 MySQL/PostgreSQL/T-SQL/Oracle native runner |
| 结果比较 | 有序结果或 multiset 结果比较、超时/大小/行数限制 |
| 保守判定 | CORRECT/WRONG/UNDECIDED 的 authoritative gate |
| Phase2 路径诊断 | 20 条核心规则、阶段排序、上游优先、primary/secondary/suppressed/unresolved |
| 教学支架 | 历史提交、行为事件、Q-matrix、L1-L4 计划和 fail-closed 回退 |
| 学习更新 | 可追溯、幂等、可回滚的 BKT/SkillObservation |
| 答案保护 | 公共 DTO、反馈渲染和 LLM validator 的答案不泄露边界 |
| LLM 接入 | 可选 Phase2 reviewer 和 Phase5 语言改写，均证据约束且可回退 |

### 16.2 已实现但必须看运行条件

| 能力 | 运行条件 |
|---|---|
| 原生 PostgreSQL | PostgreSQL URL、容器/服务、连接权限、runner 选择和真实观测 metadata 都要生效 |
| 原生 MySQL | 同上；不能只凭 dialect resolver |
| LLM | 全局/阶段开关、key、model、provider 必须存在；默认代码配置为关闭 |
| cd.members 等限定名 | 题目 catalog/标准 SQL 必须授权，不能任意放开 schema |
| CASE/LEFT JOIN 证据 | witness 生成器必须实际生成区分分支或右表悬空行，且该 world 要执行成功 |
| BKT 负向更新 | Phase2 strong evidence + 精确 rule→atomic skill 映射 |

### 16.3 当前明确的缺口或边界

1. 不能把有界测试写成全局等价证明。没找到反例只是 bounded NO_COUNTEREXAMPLE_FOUND。
2. 复杂 Phase2 映射仍不完整。EXISTS、窗口函数、UNION、CASE 等在部分情形只能标记差异或 UNCLASSIFIED_SUPPORTED_DIFF，因此跳过 BKT 是正确行为。
3. scope 可能 PARTIAL/unscoped。这表示定位不足，不是学生一定错误。
4. native 证据取决于环境。Docker compose 提供服务定义，不代表当前请求已用原生数据库。
5. SQLite rehearsal 不能替代 PostgreSQL/MySQL 原生证明。
6. 真实场景证据质量要单独验证。LEFT JOIN 必须有不匹配右表行，CASE 必须有能区分 member/guest 等分支的值；仅生成普通匹配/同分支数据不算完成验证。
7. BKT 仍为 UNCALIBRATED_MVP。工程链路完成不等于已证明教学效果。
8. LLM 默认可关闭。代码具备安全接入，不代表每个部署都在调用 LLM。

## 17. 最终判断：目前是否符合原始五阶段目的

### Phase1

在声明具体方言、具体任务和具体 schema 的教学场景中，系统已经能够：

- 解析标准/学生 SQL；
- 提取 AST 和结构差异；
- 建立 query block/scope 信息；
- 用结构差异驱动 obligation、造数、witness 和 mutation；
- 在部分场景获得标准/学生结果不同的反例证据；
- 将证据带入后续判断。

它尚不能、也不应声称完成任意 SQL 的数学等价性判定。原生方言结论必须有对应 native backend 的真实执行证据。

### Phase2

系统已经能够消费 Phase1 的结构、数据、mutation 和 witness 证据，按 SQL 教学路径归类一批常见错误，并用证据强度和依赖关系选择较早的 primary 错误点。

对未安全映射的 EXISTS、复杂窗口、UNION、CASE 或不完整 scope，系统会保留差异但不虚构具体认知归因。

### Phase3

系统已经能够读取历史提交与行为状态，计算支持需求和 L1-L4 支架计划，并在证据可信、映射明确时更新 BKT。当前 BKT 的参数和教学效果仍未完成真实学生数据校准。

### Phase4

系统已经能够根据支持需求选择 L1-L4 的教学动作，并在 lineage、规则或证据不完整时回退到安全的 L1。等级越高，反馈可以越具体，但仍禁止泄露标准 SQL。

### Phase5

系统已经具备可选的 LLM Phase2 reviewer 和 Phase5 语言改写，并有超时、JSON、ID、长度、SQL-shaped text 和确定性 fallback 约束。只有运行配置启用并成功连接 provider 时，才是实际在线 LLM 调用。

### 总结

更准确的结论是：

> 当前后端已经是一个可运行的、以安全拒判为核心的五阶段 SQL 教学判定闭环 MVP。对常见的单查询、过滤、连接、分组聚合、NULL、排序分页等教学场景，能力已经比较完整；对原生方言覆盖、复杂查询块映射、真实 witness 覆盖、LLM 生产配置和 BKT 教学效果校准，仍然需要逐项用环境证据和真实学生数据继续验证。

因此可以说“后端基础能力和绝大多数常见教学场景已经可用”，但不能把它说成“任意 SQL、任意方言、任何数据库环境和所有复杂认知错误都已完整通过”。

## 18. 复核一项能力是否真的完成的检查表

以后不要只看“测试通过”或“能 parse”，应按下面顺序核对：

1. 请求是否通过认证、字段和 attempt 幂等门禁？
2. 是否确实是一条安全的只读查询？
3. 方言是否已解析且没有冲突？
4. 标准/学生表列是否被题目 catalog 授权？
5. 使用的 backend 是什么：SQLite compatibility 还是 native？
6. native URL、容器、用户权限和隔离 schema 是否真的生效？
7. AST diff 是否有稳定 diff_id？
8. 两侧 scope 是否可靠配对，还是 PARTIAL/unscoped？
9. obligation 约束是否真实物化？
10. witness 是否实际包含需要的边界，例如悬空右表行、不同 CASE 分支？
11. 标准和学生是否都成功执行？
12. 结果差异是否被 diff_id 对应的 obligation 因果验证？
13. Phase1 是 CORRECT、WRONG 还是 UNDECIDED？
14. Phase2 candidate 是否是 supported、primary，是否存在上游抑制？
15. rule 是否有精确的 atomic skill 映射？
16. Phase3 是否应更新 BKT，还是应安全跳过？
17. L1-L4 是否由历史状态和当前证据共同决定？
18. Phase4 是否选择了不泄露答案的动作？
19. Phase5 是否真的启用、成功调用并通过 validator，还是走了 deterministic fallback？
20. 最终公共响应是否隐藏了标准 SQL、raw witness 和内部归因细节？

只有这些问题都能由日志、数据库记录、runner metadata 或测试证据回答，才可以把该能力写成“在当前环境已验证”。
