## 1. 原始五阶段目的

为避免表格中“完成”没有参照，先把原始目的编号：

| 目的编号 | 原始目的 |
|---|---|
| O1 | 在声明具体 SQL 方言、查询任务和 schema 的前提下，解析标准 SQL 与学生 SQL 的结构，用结构驱动造数、变异和消融，在一定场景中找到反例证据，辅助判断两条 SQL 是否不等价。 |
| O2 | 综合 Phase1 的结构、数据、变异和消融证据，按照 SQL 教学逻辑路径归类学生错误，并找到较早、较上游且有证据支持的偏离点。 |
| O3 | 根据学生历史提交、行为事件和最新提交，计算当前支持需求、知识点优先级以及应当使用的支架深度。 |
| O4 | 根据 L1/L2/L3/L4 支架级别决定反馈具体程度，同时不泄露正确 SQL。 |
| O5 | 让 LLM 在受控证据和已批准教学动作范围内生成自然、有启发性且不泄露题目 SQL 答案的反馈。 |

API 的安全、认证、幂等和数据库隔离不是额外的教学阶段，但它们是 O1 到 O5 能安全运行的前置条件。

## 2. 两个状态必须分开看

表格中的“实现状态”和“验证状态”不是一回事。

### 2.1 实现状态

- **已实现**：代码路径存在，功能行为已经写入后端。
- **条件实现**：代码路径存在，但必须有 Docker、数据库 URL、权限、LLM provider 等运行条件。
- **部分实现**：常见场景能够处理，但复杂场景、映射或输出证据还不完整。
- **安全边界**：系统有意拒绝无法可靠判断的情况，不能把这种拒绝写成缺陷。

### 2.2 验证状态

- **自动化验证**：有对应测试，能够重复证明代码行为。
- **兼容验证**：主要通过 SQLite compatibility rehearsal 验证，不能替代目标数据库原生验证。
- **原生环境待验证**：代码已具备，但还需要 PostgreSQL/MySQL 等真实 runner 的运行证据。
- **场景证据缺口**：策略存在，但样本没有真正触发目标条件，例如没有悬空右表行或没有区分 CASE 分支的值。
- **效果未校准**：工程链路已经存在，但还没有真实学生数据和离线校准。

只有“实现状态已实现/条件实现”与“验证状态自动化验证/目标环境验证”同时满足时，才适合对外说“该能力已验证”。否则应使用“代码已具备”“条件支持”或“部分验证”。

## 3. 完整系统流程总览

~~~text
POST /ai/check-sql
  1. 认证、请求字段门禁、attempt 单飞
  2. 读取题目和 schema，检查 attempt 幂等与请求指纹
  3. 第一轮学生 SQL 安全检查
       ├─ 安全违规：写安全分支记录，返回固定 L1 系统提示
       └─ 通过/限定名待题目授权：继续
  4. 解析标准 SQL、学生 SQL 的方言和语法
       ├─ 学生语法错误：写语法反馈，不进入语义 BKT
       ├─ 标准语法/平台错误：平台错误，停止
       └─ 两侧可解析：继续 Phase1
  5. Phase1
       schema/catalog
       AST / SQLStructureIR / scope
       AST diff / stable diff_id
       obligation / witness / mutation
       SQLite compatibility 或 native runner
       结果比较和 authoritative decision
       ├─ CORRECT：继续 Phase2 正确包
       ├─ WRONG：继续 Phase2 错因诊断
       └─ UNDECIDED：HTTP 422，停止学习更新
  6. Phase2
       读取 Phase1 证据
       按教学阶段生成候选错误
       找较早 primary，抑制下游症状
       生成确定性诊断包，必要时调用受控 LLM reviewer
  7. Phase3
       读取历史提交和行为事件
       计算支持需求、技能优先级和支架等级
       只对证据强且映射明确的技能准备 BKT 观察
  8. Phase4
       按 CORRECT/WRONG、candidate、rule、stage 和 L1-L4 选择教学动作
       lineage 不完整时回退安全 L1
  9. Phase5
       可选 LLM 只改写获准的教学动作
       超时、错误、答案风险时回退确定性文案
 10. 最终数据库锁、幂等复核、Submission/审计/BKT/反馈快照写入
 11. 返回隐藏内部证据的公共响应
~~~

安全拦截、语法错误、平台失败和 Phase1 UNDECIDED 不会完整走完五个 Phase。是否继续往下走由上一步的 authoritative 状态决定。

## 13. 当前真实流程中各术语的具体含义

### 13.1 SQLStructureIR 与 scope graph 不是同一个东西

SQLStructureIR 是“把一棵 SQL AST 总结成结构特征”的对象，例如它能表示这条 SQL 有 WHERE、两个 JOIN、一个聚合和一个窗口函数。当前它主要出现在：

~~~text
Phase1 判定 WRONG
  -> error attribution 辅助路径
  -> SQLStructureIR.from_ast
  -> structural knowledge points
~~~

scope metadata/ScopedQueryGraph 则回答“这个 WHERE 属于哪个 SELECT”。它会记录 ROOT、CTE、DERIVED、SUBQUERY、SET_BRANCH、scope_id、conceptual_scope_id 和查询块之间的边，供 Phase2 绑定差异位置。

因此，当前准确说法是：

> SQLStructureIR 已实现，并在错误归因辅助路径使用；scope graph 已实现，并在 Phase2 诊断中用于查询块定位。SQLStructureIR 不是当前 Phase2 主诊断图。

### 13.2 scope_id、conceptual_scope_id 和 unscoped

以标准 SQL 和学生 SQL 各自有一个根查询为例：

~~~text
standard:root
student:root
~~~

这是两个侧别不同的 scope_id。只有两边结构路径和块类型可靠一致时，才会有共同 conceptual_scope_id。

如果标准 SQL 有一个 CTE，而学生 SQL 没有对应 CTE：

~~~text
standard:root/cte:recent
student: 没有对应块
~~~

系统不能强行将标准 CTE 合并到学生 ROOT。此时 PARTIAL/unscoped 的意思是“定位信息不足”，不是“学生一定写错”。

### 13.3 LATERAL_TO

普通派生表通常不能引用外部或左侧来源；LATERAL 允许左侧来源可见：

~~~sql
FROM members AS m
JOIN LATERAL (
  SELECT ...
  WHERE ... = m.id
) AS x ON true
~~~

内层查询使用 m.id，因此 graph 需要记录 LATERAL_TO 或相关依赖。这说明的是查询块之间的可见性/依赖关系，不是把两个 SELECT 合并成一层。

### 13.4 obligation、witness 和 mutation

- **obligation**：一个待验证的证据目标，例如“构造 credits=3，使 > 和 >= 产生不同结果”。
- **witness**：满足 obligation 的具体数据世界，例如某张表中放入边界值、NULL、悬空右表行或两个 CASE 分支值。
- **mutation**：有控制地替换某一个结构因素，例如把一个 JOIN 条件换成候选条件，再观察结果是否修复/保持等价。

三者通过 stable diff_id 关联。约束没有真实物化、两侧没有成功执行或没有因果区分时，都不能写成强反例证据。

### 13.5 primary 与最上游错误点

“最上游”不是说系统知道了学生思维的唯一心理原因，而是：

1. 按 SQL 教学阶段把候选排序；
2. 查看候选之间的依赖；
3. 优先选择更早且有 CAUSAL_VERIFIED/REPAIR_VERIFIED 的候选；
4. 将由它解释的下游异常标为 suppressed；
5. 没有足够证据则标 unresolved。

例如 JOIN fanout 导致 COUNT 变大时，若 JOIN 证据充分，JOIN 是 primary，COUNT 异常是下游症状；若 JOIN 证据不足，则不能强行更新 join skill。

## 17. 本版结论

当前系统可以准确描述为：

> 一个已经形成 API、安全门禁、方言解析、结构差异、受约束造数、witness/mutation、有限执行、保守判定、Phase2 路径诊断、Phase3 支架/BKT、Phase4 教学动作和可选 Phase5 LLM 的 SQL 教学后端闭环。

它已经不是只有设计文档或只会 parse 的原型。对常见单查询、过滤、连接、分组聚合、NULL、排序分页等教学场景，后端基础能力已经比较完整。

但当前不能笼统写成“所有阶段全部完成”或“PostgreSQL 路由已完全通过”。准确的表达必须保留以下边界：

1. Phase1 是具体任务、schema、方言和有界 world 下的证据判定，不是任意 SQL 的数学等价性证明；
2. SQLStructureIR 是已实现的错误归因辅助结构，不是当前 Phase2 主诊断图；
3. scope 配不上时的 PARTIAL/unscoped 表示定位不足，不表示学生一定写错；
4. SQLite compatibility 不能替代 PostgreSQL/MySQL native；
5. LEFT JOIN 悬空行和 CASE 分支要有真实 fixture 证据，不能只看策略名称；
6. EXISTS、窗口、UNION、CASE 等复杂差异在不能安全映射时应跳过 BKT；
7. BKT 工程闭环已存在，但仍是 UNCALIBRATED_MVP；
8. LLM 已接入安全边界，但默认可关闭，实际在线调用需要运行配置和 provider 证据。

因此，当前最稳妥的总体状态是：

> 工程闭环基本成立，常见教学场景可用；原生多方言覆盖、复杂结构认知映射、真实 witness 覆盖和学习效果校准仍处于条件验证或部分完成阶段。
