更新时间：2026-08-29

## 1. 为什么论文需要结构化表达

当前系统不是单一的 SQL parser，而是一条包含安全门禁、方言解析、结构比较、受约束造数、数据库执行、证据判定、错因诊断、学习状态更新和教学反馈的多阶段管线。

如果只用自然语言写成：

> 系统分析学生 SQL，找出错误，然后使用 LLM 反馈。

读者无法知道：

- SQL 是如何进入系统的；
- 解析成功后为什么还可能不能执行；
- 结构差异如何转成数据约束；
- 反例来自 SQLite 还是 PostgreSQL；
- 为什么有时系统返回 UNDECIDED；
- 为什么 Phase2 能识别差异，却不一定更新 BKT；
- LLM 到底能不能改变判定；
- 支架等级如何由历史提交得到。

因此论文至少需要四层表达：


| 内容              | 推荐表达方式                            | 本系统中的作用                                  |
| --------------- | --------------------------------- | ---------------------------------------- |
| SQL 支持的结构范围     | 上下文无关语法/EBNF                      | 说明系统关注哪些 SELECT、JOIN、聚合、子查询、集合和分页结构      |
| AST、查询块、作用域     | 带属性的语法树和图                         | 说明结构节点属于哪一个查询块，以及两侧能否可靠配对                |
| Phase1 到 Phase5 | 函数组合、数据流图或状态转移                    | 说明输入怎样经过门禁、证据、诊断、学习和反馈                   |
| 标准/学生差异         | diff 集合和 stable diff_id           | 说明一个差异如何跨越 AST、witness、mutation 和 Phase2 |
| 造数与执行           | obligation、witness world、evidence | 说明结构差异如何变成可执行的具体数据和结果证据                  |
| Phase2 错误诊断     | 有向依赖图和路径排序                        | 说明怎样从多个候选中选择较早的 primary 错误               |
| Phase3 支架       | 历史状态到支持需求的函数                      | 说明历史提交、行为和 BKT 怎样影响 L1-L4                |
| Phase4/5 反馈     | 受约束动作选择和 LLM 改写函数                 | 说明反馈可以变具体，但不能改变证据或泄露答案                   |


关键原则是：

> 上下文无关语法适合表示 SQL 的句法范围，不适合单独表示整个教学系统。完整论文应当组合使用 EBNF、属性 AST、查询块图、数据流函数、状态转移和约束表。

## 2. 论文的基本任务模型



### 2.1 教学任务

定义一个具体 SQL 教学任务：

\tau=(d,C,q^r,Q,QM)

其中：

- d：目标 SQL 方言和版本；
- C：题目 schema/catalog；
- q^r：reference/standard SQL；
- Q：自然语言查询任务；
- QM：题目到知识点的 Q-matrix。

这里的 C 不只是表名列表，还可以包含：

- 表和列；
- 数据类型；
- 可空性；
- 主键和唯一键；
- 外键；
- 表之间的关系；
- bridge/fanout 等造数信息；
- 允许的 schema/catalog namespace。



### 2.2 学生请求

学生提交定义为：

x=(q^s,u,a,\ell,H_t)

其中：

- q^s：student SQL；
- u：当前用户；
- a：attempt_id；
- \ell：反馈语言；
- H_t：截至当前时刻的历史提交与行为状态。

系统的输出不是只有一个布尔值，而是：

y=(J,D,N,L,A,F,P)

其中：

- J：Phase1 authoritative judgment；
- D：Phase2 diagnostic package；
- N：Phase3 support need；
- L：支架等级；
- A：Phase4 教学动作；
- F：Phase5 学生反馈；
- P：持久化和公共响应状态。



### 2.3 输出判断的边界

本系统不定义任意 SQL 的数学等价性证明。它定义的是给定任务和有限测试世界下的 operational judgment：

J_{\tau,B,W}(q^r,q^s)

其中：

- \tau 是具体任务；
- B 是实际执行后端；
- W 是有限 witness worlds。

因此论文中应使用：

- bounded evidence；
- operational acceptance；
- counterexample-supported non-equivalence；
- undecided under insufficient evidence。

不应直接写成：

> 系统证明了两条任意 SQL 在数学上等价。

## 3. SQL 支持范围：用 EBNF 表达，而不是声称完整 SQL 标准



### 3.1 为什么用简化语法

完整 SQL 标准和各厂商方言非常庞大。论文需要说明系统实际分析的结构边界，而不是声称实现了完整 SQL grammar。

下面是适合论文使用的抽象 EBNF。它是论文中的“结构子集语法”，用来说明系统关注哪些查询结构；它不是 SQLGlot 的内部 parser grammar，也不是完整 SQL 标准：

这段语法表达的是系统需要关注的结构族：

- 根查询；
- CTE；
- 派生表；
- 子查询；
- LATERAL；
- JOIN；
- WHERE；
- GROUP/HAVING；
- WINDOW/QUALIFY；
- CASE；
- UNION/INTERSECT/EXCEPT；
- ORDER/LIMIT/OFFSET。

它不表示每一种厂商扩展都已被完整支持。具体方言仍由 dialect resolver、schema/catalog、安全策略和执行 runner 共同决定。名称是否存在、列是否可见、子查询是否相关、查询是否允许执行等约束，不由这段上下文无关语法单独决定，而由后面的属性检查和运行时证据决定。

### 3.2 语法能表达什么，不能表达什么

EBNF 能表达：

- 一个结构是否属于 SELECT；
- JOIN、GROUP、HAVING、WINDOW 等是否存在；
- set branch、derived table、subquery 等句法嵌套。

EBNF 不能单独表达：

- cd.members 是否被题目 catalog 授权；
- 内层子查询是否引用外层列；
- 两侧查询块是否是同一概念位置；
- PostgreSQL 和 SQLite 的语义差异；
- 查询是否安全、是否允许执行；
- 某个差异是否真的造成结果不同。

因此需要属性和图模型。

## 4. 带属性的 AST 和查询块图

本节先定义论文使用的对象和关系，不表示它们已经按此顺序执行；真实运行顺序以第 6 至第 9 节为准。

### 4.1 AST 的属性

标准 SQL 和学生 SQL 分别解析为：

A^r=P_d(q^r),\qquad A^s=P_d(q^s)

其中 P_d 是方言 d 下的 parser。

每个 AST 节点可以抽象带有如下属性：

attr(n)=
(clause,target,datatype,alias,side,scope)

实际系统关心的属性包括：

- clause：SELECT、WHERE、JOIN、GROUP、HAVING、ORDER 等；
- target：目标表或列；
- alias：表别名；
- datatype：schema/catalog 推导的类型；
- side：standard 或 student；
- scope：节点所属查询块；
- extra：方言或结构附加信息。



### 4.2 SQLStructureIR 的准确位置

SQLStructureIR 可以形式化为：

I(q)=IR(A(q))

它是对 AST 的结构特征摘要。例如：

I(q)=

\text{WHERE},
\text{JOIN}_2,
\text{AGGREGATE},
\text{WINDOW}

它可以包含：

- projection；
- DISTINCT；
- WHERE；
- JOIN；
- GROUP BY；
- HAVING；
- ORDER BY；
- LIMIT/OFFSET；
- subquery；
- CTE；
- set operation；
- CASE；
- window；
- predicate/logic tree；
- aggregate；
- expression；
- table reference；
- named window；
- DISTINCT ON；
- QUALIFY；
- grouping sets、ROLLUP、CUBE；
- recursive、LATERAL、hierarchy、pivot、sample 等扩展信息。

论文中的准确表述应为：

> SQLStructureIR is an auxiliary structural representation used on the WRONG attribution path. The main Phase1 evidence chain is driven by AST differences, obligation compilation, witness generation, mutation, and execution comparison.

不能写成：

> SQLStructureIR 驱动了整个 Phase1 的造数、变异和 Phase2。

一个 Query Block 是一个独立 SELECT 语义范围。抽象表示为：

QB=(kind,body,scopeid)

常见 kind 是：

ROOT,CTE,DERIVED,SUBQUERY,SETBRANCH

例如：

Query Block 解决的是“哪一层 SELECT”的问题。外层 WHERE、CTE 内部 WHERE 和 EXISTS 内部 WHERE 即使语法相似，也可能属于不同 block。

### 4.4 两类作用域信息与 Scope Graph

“作用域”在当前实现中有两个不同的使用时点，论文中不能把它们合并成一个步骤：

1. analyze_schema_qualification() 在 schema qualification 时，为每个 SELECT 建立内部 QueryScope，用于判断当前查询块能看到哪些表、别名和外层相关引用；这是资格检查的中间信息。
2. 主比较完成后，_build_phase1_scope_metadata() 才从两侧 AST 和 ast_diffs 生成对外挂载的 scope_metadata，其中包含 scopes、conceptual_scopes、边和 diff_bindings；Phase2 再用它构建 ScopedQueryGraph。

因此，形式化表示为：

Q_C^{side}=Qualify(A^{side},C)
\quad\text{（早期资格检查中的 QueryScope）}

S_{meta}=BuildScopeMetadata(A^r,A^s,\Delta_{AST})
\quad\text{（Phase1 末尾挂载到 SandboxRun 的元数据）}

Phase2 的图构建是：

G_{scoped}=BuildScopedQueryGraph(S_{meta})

BuildScopedQueryGraph 只消费已经生成的作用域元数据，不重新解析 SQL，也不执行 SQL。查询块图可以写成：

G^{side}=(V^{side},E^{side})

节点：

v=(kind,side,scopeid,path,metadata)

其中：

- kind 是 ROOT/CTE/DERIVED/SUBQUERY/SET_BRANCH 等；
- side 是 standard 或 student；
- scope_id 是本侧定位 ID；
- path 是结构路径；
- metadata 是解析和绑定附加信息。



### 4.5 scope_id

scope_id 是侧别感知的查询块 ID，例如：

### 4.6 conceptual_scope_id

只有标准侧和学生侧在结构路径、block 类型等方面可靠对应时，才定义：

pair(v^r,v^s)
\Rightarrow conceptualscopeid

它回答：

> 这两个侧别的查询块能否被认为是同一个概念位置？

如果标准 SQL 有 CTE，而学生 SQL 没有对应 CTE，就不能把标准 CTE 强行合并到学生 ROOT。

## 5. 标准/学生差异：diff 集合和 stable diff_id

本节定义差异对象及其跨阶段关联方式；它不是把 scope binding 提前到 obligation 编译之前。实际时序由第 6.1 节给出。

### 5.1 差异集合

Phase1-3 的 AST 结构差异写成：

\Delta_{AST}=Diff(A^r,A^s)

作用域元数据不是此处提前生成。Phase1-3 先把差异结果规范化为：

\Delta_{AST}=\delta_i^{AST}_{i=1}^{n}

其中每个原始差异可表示为：

\delta_i^{AST}=(clause,difftype,target,node^r,node^s,kp)

随后在 Phase1-9 生成 S_{meta}；Phase2 消费该元数据后，才进行定位绑定：

\Delta=BindScope(\Delta_{AST},S_{meta})

其中：

- \delta_i^{AST} 是 Phase1-3 只依据两侧 SQL 结构提取的原始差异；
- S_{meta} 是 Phase1-9 挂载到 SandboxRun.data_evidence 的作用域元数据；
- \Delta 才是 Phase2 使用的、尽可能带有查询块定位的差异集合。

一条差异可以表示为：

\delta_i=
(clause,difftype,target,node^r,node^s,kp,scopebinding)

如果无法可靠配对查询块，scope_binding 可以为空或为 unscoped；这表示定位证据不足，不是学生错误结论。

实际可识别的差异包括：

- projection；
- WHERE 谓词；
- JOIN 类型；
- JOIN ON 条件；
- GROUP BY；
- HAVING；
- aggregate；
- DISTINCT；
- CASE；
- window；
- ORDER BY；
- LIMIT/OFFSET；
- subquery/EXISTS/IN；
- correlated query；
- CTE；
- set operation；
- NULL；
- LIKE/regex。

### 5.3 差异和等价性不是同一个命题

\delta_i\neq\varnothing

只说明结构不同，不直接说明：

Result(q^r)\neq Result(q^s)

因为：

- 结构不同可能在所有当前数据上结果相同；
- 结构相同可能因方言语义不同产生不同结果；
- 需要有界 witness 或 native execution 才能形成运行证据。

## 6. Phase1：用函数组合展示完整证据链



### 6.1 按真实运行顺序表示主流程

论文中的 Phase1 不应把 ScopeBuild 放在 AST diff 和 obligation 之前。当前后端的主链可以抽象为：

x=(q^r,q^s,\hat d,C,H_t)

\begin{aligned}
x
&\xrightarrow{P1\text{-}1}
R=(A^r,A^s,\rho_d)
&\xrightarrow{P1\text{-}2}
Q=(Q_C^r,Q_C^s)
&\xrightarrow{P1\text{-}3}
\Delta_{AST}
&\xrightarrow{P1\text{-}4}
O
&\xrightarrow{P1\text{-}5}
(T,W)
&\xrightarrow{P1\text{-}6}
E_B
&\xrightarrow{P1\text{-}7}
M
&\xrightarrow{P1\text{-}8}
J_{p1}
&\xrightarrow{P1\text{-}9}
S_{meta}
&\xrightarrow{Phase2}
D
&\xrightarrow{Phase3}
(N,L)
&\xrightarrow{Phase4}
A
&\xrightarrow{Phase5}
F
\end{aligned}

各符号在当前实现中的含义是：


| 符号           | 当前真实产物                                                 | 下游用途                               |
| ------------ | ------------------------------------------------------ | ---------------------------------- |
| R            | 两侧严格解析得到的 Query AST A^r,A^s 和方言决议记录 \rho_d             | schema qualification、结构比较和执行准备     |
| Q            | 两侧 SchemaQualification；其中含有资格检查期间建立的内部 QueryScope      | 判断表、列、别名和相关引用是否具备后续处理资格            |
| \Delta_{AST} | extract_ast_diffs() 返回的 ASTDiffNode 列表                 | 编译 obligation；不是等价性结论              |
| O            | compile_obligations() 生成的 DistinguishingObligation 列表  | 描述需要什么数据条件才能暴露差异                   |
| T,W          | 造数策略/StrategyDeclaration、WitnessSuite 和 WitnessWorld   | 生成并物化有界测试数据                        |
| E_B          | SandboxRun、data_evidence 和执行结果                         | 比较标准/学生结果，形成运行证据                   |
| M            | mutation_evidence                                      | 补充替换、移除和修复证据                       |
| J_{p1}       | Phase1 的有界判断和 API 对外状态                                 | 决定是否可以安全进入后续诊断                     |
| S_{meta}     | Phase1 末尾附加到 SandboxRun.data_evidence 的 scope_metadata | Phase2 构建 ScopedQueryGraph 并绑定差异位置 |


工程实现还会在方言决议之后、schema qualification 之前选择 execution backend，并执行 unsupported-feature gate；没有可用的 vendor backend 时返回 ENGINE_GAP，命中不支持特征时返回 UNSUPPORTED。这些是后续执行资格门禁，不是语义等价性证据。

这里的箭头表示逻辑上的处理顺序，不表示每一步都是一个独立 HTTP 接口。实现上，generate_witness_suite() 会在一次调用中继续调用 compile_obligations()、策略规划和 world 物化；_complete_comparison() 会完成执行比较、mutation 和 Phase1 结果整理。早期 qualification 使用的 QueryScope 与末尾的 scope_metadata 是两个不同产物；后者不是 obligation 编译的输入，也不是提前生成的 Phase2 图。



### 6.2 Phase1-1a：输入门禁

输入门禁可以写成：

Gate(x)\in
ACCEPT,REJECT

其中包括：

- 身份认证；
- SQL 长度；
- question_id；
- attempt_id；
- language；
- 额外字段；
- attempt 单飞；
- 请求幂等。

这一层判断“请求是否合法”，不是判断“SQL 是否正确”。

### 6.3 Phase1-1b：安全门禁

安全函数可以写成：

Safe(q^s)=
\begin{cases}
REJECT,&\text{multi-statement/DML/DDL/dangerous}
DEFERREDNAMESPACE,&\text{qualified name needs catalog}
PASS,&\text{otherwise}
\end{cases}

### 6.4 Phase1-1c：严格解析、方言决议与执行资格

方言解析：

ResolveDialect(q^r,q^s,\hat d)
\rightarrow
RESOLVED,CONFLICT,SYNTAXERROR,UNSUPPORTED

解析成功后得到 A^r=P_d(q^r) 和 A^s=P_d(q^s)，每侧要求是单条、完整、只读的 Query AST。解析成功只说明可以进入后续资格门禁，不授予 SQL 执行资格；执行仍要经过 backend、namespace 和原生查询安全检查。

学生侧语法错误作为提交错误返回；标准 SQL 解析失败作为题目/平台输入问题处理；方言冲突、未支持方言或未支持方言特征停止后续证据链。



只有两侧在可接受的方言和语法状态下，才进入后续结构比较。

### 6.5 Phase1-2：schema/catalog 资格检查

两侧分别进行 schema qualification：

Q_C^{side}=Qualify(A^{side},C)

当前实现的主要动作是：

- 为每个 SELECT 建立资格检查用的内部 QueryScope；
- 识别 FROM/JOIN 中的物理表、表别名、CTE 和派生关系；
- 检查物理表、限定列、非限定列是否存在或产生歧义；
- 对相关子查询继承外层可见的表别名；
- 结合 authoritative SchemaCatalog 判断题目允许的物理表和列。

结果抽象为：

Q_C^{side}\in
QUALIFIED,NOTQUALIFIED,BOUNDARY

这一步是 cd.members、cd.bookings 这类限定名能否继续进入执行准备的关键。点号本身不代表危险或合法；只有题目 catalog 能证明它对应受信的教学物理表时，后续 namespace rewrite 才可以授权。受信 namespace 映射属于执行准备阶段，不是 SchemaQualification 的字段；执行准备仍可能另外产生 SECURITY_REJECTED。CTE 和派生表的输出列当前不做完整静态展开，部分名称解析仍由后续原生引擎完成。

标准侧 qualification 失败时停止后续证据生成，并作为 INPUT_ERROR/INPUT_GAP 处理；未知或越权 namespace fail-closed。原生 backend 下，学生侧缺失列可以交给 PostgreSQL/MySQL 等原生引擎判定，并保留 student_exec_error，不能在这里提前伪装成普通语义错误；SQLite compatibility 结果也不能冒充原生方言证据。

### 6.6 Phase1-3：AST 结构差异提取

schema/catalog qualification 通过后，调用：

\Delta_{AST}
=extractastdiffs(q^r,q^s;d,C)

实现上的 extract_ast_diffs() 接收标准 SQL、学生 SQL 和已确定的解析/语义方言，并在函数内部重新解析两侧 SQL 后，运行当前已实现的差异提取器。它产生 ASTDiffNode 列表，记录标准侧与学生侧在投影、谓词、JOIN、分组、排序、分页、聚合、CASE、窗口、CTE、子查询、相关查询和集合操作等结构上的差异。

每个原子差异至少抽象包含：

\delta_i^{AST}=
(difftype,clause,target,node^r,node^s,kp)

这里的 \Delta_{AST} 只是“结构哪里不同”的清单，不是语义等价性结论。没有可靠的 ast_diff 时，后续不能凭空生成对应的语义 obligation，也不能因此直接判定学生一定写错。

SQLStructureIR 的辅助路径写成：

I^r=SQLStructureIR(A^r),\qquad
I^s=SQLStructureIR(A^s)

它是错误归因路径中的结构特征摘要，不是当前 Phase1 主 witness 链的唯一输入；主链使用 \Delta_{AST} 继续进入 obligation、witness、执行和 mutation。

### 6.7 Phase1-4：obligation 编译

在当前主流程中，generate_witness_suite() 接收 ast_diffs，并在内部调用 compile_obligations()。形式化表示为：

O=CompileObligations(
\Delta_{AST},
C,
Q_C^r,
Q_C^s
)

实际的 compile_obligations() 遍历非冗余差异，推断涉及的表和列，计算 stable diff_id，并尝试按照差异类型匹配约束模板。obligation 不是“学生错了”的结论，而是一个证据目标：

专用模板可以把 >→>= 编译成边界值约束，把 INNER JOIN→LEFT JOIN 编译成无匹配右表行约束，把 COUNT(*)→COUNT(col) 编译成 NULL 约束。没有专用模板时，当前实现可能生成 generic fallback obligation，例如 observable_projection_discriminator；它只是待验证的证据任务，不代表已经获得语义证据。

每个 DistinguishingObligation 记录：

- obligation_id，以及关联的 diff_id；
- diff_type、clause、知识点；
- 需要的表和列；
- minimum_rows；
- hard_constraints 和通常为空的 soft_constraints；
- success_predicate（通常是标准结果与学生结果不同）；
- 估计成本、冲突或诊断信息。

obligation 编译不直接造数、不执行 SQL，也不做等价性判定。late scope_metadata/ScopedQueryGraph 不是这个函数的输入；这里只使用 qualification 结果帮助判断表列可用性。





如果差异无法可靠关联到目标表列，或者 fallback 任务后续无法满足和验证，它会在后续保持 uncovered/gap，最终只能导向 UNDECIDED/KNOWN_GAP；不能把“生成了 obligation”写成“已经证明学生错误”，也不能把“没有生成反例”写成“两条 SQL 已被证明等价”。

### 7.1 Phase1-5：witness world

有限测试世界集合：

W=w_1,w_2,\ldots,w_k

当前 planner 对 world 数量有界，常见上限约为 8。每个 world 包含：

其中：

- O_i：关联 obligation；
- \Gamma_i：数据约束；
- D_i：生成的 fixture 数据；
- P_i：生成 provenance、诊断和未覆盖任务等规划信息。

执行 backend B 和标准/学生查询结果属于后续 E_B，不把尚未执行的 world 误写成已经产生了运行结果。





### 7.2 Phase1-5：ConstraintLedger

多个 obligation 可能要求同一个字段具有互相冲突的值。ConstraintLedger 处理：

Merge(\Gamma_i,\Gamma_j)=
\begin{cases}
\Gamma_i\cup\Gamma_j,&\text{无冲突}
Split(w_i,w_j),&\text{有冲突}
\end{cases}

它不会静默覆盖旧值。这样可以防止生成一个表面满足所有 obligation、实际没有满足任何一个目标的伪世界。

### 7.6 Phase1-6：SQLite compatibility

兼容执行可以写成：

R^{compat}*w=
Compare(
Exec*{SQLite}(Rewrite(q^r),w),
Exec_{SQLite}(Rewrite(q^s),w)
)

它适合：

- 开发和回归；
- 有界结构差异验证；
- 没有原生数据库时的 rehearsal。

它不能单独证明：

- PostgreSQL 特有类型；
- PostgreSQL schema/权限；
- PostgreSQL planner；
- PostgreSQL 全部排序、NULL 和函数语义。



### 7.7 Phase1-6：PostgreSQL native

原生 PostgreSQL 执行可以写成：

R^{pg}*w=
Compare(
Exec*{PostgreSQL}(q^r,\sigma_w),
Exec_{PostgreSQL}(q^s,\sigma_w)
)

其中 \sigma_w 是隔离执行上下文，包括：

- 随机 schema；
- 受限 reader/role；
- search_path；
- 必要权限；
- transaction/savepoint；
- 查询超时；
- 结果行数/大小上限；
- 回滚和清理。

真实 PostgreSQL 完整路由必须验证：

1. PostgreSQL 容器运行；
2. PARSEVAL_POSTGRES_URL 生效；
3. 方言确认为 PostgreSQL；
4. cd.members、cd.bookings 通过题目 catalog；
5. native backend metadata 为 postgres；
6. qualified names 能在隔离 schema 执行；
7. LEFT JOIN 真实产生悬空右表行；
8. CASE 真实覆盖不同分支；
9. 执行后角色、schema 和数据清理。



### 7.8 Phase1-6：执行结果比较

有根查询 ORDER BY 时：

Compare_{ordered}(R^r,R^s)

比较列和有序行。

没有根查询 ORDER BY 时：

Compare_{multiset}(R^r,R^s)

比较列和多重集合，避免把数据库任意返回顺序误当成语义差异。

### 7.9 Phase1-7：运行时变异隔离

在已选 witness world 和同一 query block 中，运行时 mutation 对学生 SQL 做受限变体：

q_{i}^{s,replace}
=Replace(q^s,\delta_i,node_i^r)

q_{i}^{s,remove}
=Remove(q^s,\delta_i)

随后在同一数据条件和同一 backend 下重新执行，并比较：

M_i=
Compare(
Exec_B(q^r,D_w),
Exec_B(q_{i}^{s},D_w)
)

当前实现会记录 replacement/removal 的执行状态、是否恢复标准结果、fixed_by_replacement、removed_student_clause_equivalent、query_scope、mutation_scope、dependent_changes，以及关联的 diff_id/obligation_id。它覆盖 WHERE、GROUP/HAVING、ORDER/LIMIT、JOIN、CASE、窗口、子查询、集合等变异处理器。

只有“单个可可靠绑定的节点替换后恢复标准结果”才可作为较强的 repair/causal evidence。变异 SQL 执行失败、需要同时修改多个依赖节点、多个错误互相遮蔽，或仅仅在当前 world 中移除后仍等价时，只保留不确定的 pair-level/repair evidence；不能升级成全局因果证明，也不能把当前 world 的冗余现象当成学生必然正确。

\begin{cases}

WRONG,&\text{teachable NOTEQUIVALENT}

### 8.4 Phase1-9：生成作用域元数据并交给 Phase2

当前结果挂载在：

SandboxRun.dataevidence["scopemetadata"]

其中包含两侧的 scopes、可靠配对后的 conceptual_scopes、PARENT 和 composition edges、diff_bindings、limitations、status 以及 truncated。它使用 standard/student 侧的 scope_id；只有查询块能够可靠配对时才产生 conceptual_scope_id。差异无法可靠定位时使用 limitation 或 unscoped 标记。

### 9.5 primary、secondary、suppressed、unresolved

> 在当前证据图和教学路径中，选择最早且证据充分、能够解释后续现象的候选节点。

## 10. Phase3：历史状态到支持需求的函数



### 10.1 历史状态

定义学生状态：

H_t=

其中：

- S_t：最近语义提交；
- B_t：行为事件，如提示使用、语法错误、安全拦截；
- K_t：当前 BKT 技能状态；
- Q_t：当前题目 Q-matrix 和诊断信息。

当前通常读取最近约 10 个语义/行为事件，处理 idle reset、recurrence decay 和 failure streak。

### 10.2 负向观察的条件

负向技能观察不是由“出现一个 SQL diff”直接产生，而是需要：

NegObs(skill)=
\begin{cases}
1,&
\begin{array}{l}
diagnosis=INCORRECT
candidate=PRIMARY
evidence\inCAUSALVERIFIED,REPAIRVERIFIED
rule\rightarrow skill\text{ 是精确映射}
scope\text{ 和 lineage\text{ 可靠}
\end{array}
0,&\text{otherwise}
\end{cases}

因此以下内容会跳过 BKT：

- 只有结构差异；
- 只有弱输出差异；
- scope 是 partial/unscoped；
- candidate 是 suppressed/unresolved；
- EXISTS、窗口、UNION、CASE 尚未有精确 atomic mapping；
- 平台、语法、安全和执行错误。



### 10.3 正向观察

- event id：保证幂等；
- lock：保证并发安全；
- rollback：学习写失败时只回滚学习更新。

当前状态必须标为：

> 工程闭环已实现，但 BKT 仍处于 UNCALIBRATED_MVP，教学效果尚未由真实学生数据证明。

## 11. Phase4/5：受约束动作选择和 LLM 改写



### 11.1 Phase4 动作函数

可以定义：

A_t=SelectActions(J,D,L_t)

其中动作选择必须检查：

- verdict 是否匹配；
- candidate 是否存在；
- rule/stage/logical path 是否与 Phase3 对齐；
- 是否存在可靠 evidence lineage；
- 是否为 unresolved/unscoped-only。







### 11.2 L1-L4 动作集合

可以将动作集合表示为：

\mathcal{A}(L)=
\begin{cases}
directionalSocratic,&L1
behaviorlocalizedSocratic,&L2
witnessconflictSocratic,&L3
rulerepairreflectionSocratic,&L4
\end{cases}

所有动作都满足：

answerrevealed(A)=false

### 11.3 fail-closed

如果 candidate、lineage 或动作选择失败：

SelectActionserror
\rightarrow
SYSTEMNOTICE,L1

系统退回一个安全的 L1，而不是生成可能指错方向的高等级教学。

### 11.4 Phase5 确定性反馈

确定性反馈函数：

F_{det}=Render(A)

渲染器负责：

- segment 标签；
- 最大长度约 16KB；
- feedback hash；
- answer_revealed=false；
- 隐藏规则、skill、candidate、witness 和 Q-matrix。







### 11.5 Phase2 LLM reviewer

Phase2 LLM 可以形式化为：

D'=
Validate(
LLM_{review}(
Q,C,q^r,q^s,
Summary_{p1},
D,E
))

但它受到约束：

Verdict(D')=Verdict(D)

Evidence(D')\subseteq Evidence(D)

Skills(D')\subseteq Skills_{approved}(D)

LLM 可以：

- 在已有候选中排序；
- 改写叙事；
- 组织 witness 解释。

LLM 不可以：

- 改变 Phase1 authoritative verdict；
- 凭空增加 witness；
- 新增 skill；
- 把弱证据变成强证据；
- 把标准 SQL 返回给学生。



### 11.6 Phase5 LLM rewrite

Phase5 只改写获准动作：

F=
\begin{cases}
F_{det},&LLM\ disabled/error
Validate(LLM_{rewrite}(A)),&LLM\ enabled
\end{cases}

固定动作如 ACCEPTANCE、SYSTEM_NOTICE、SOCRATIC 不被自由替换；可编辑动作必须通过：

- action ID 校验；
- JSON 校验；
- 长度校验；
- 相似度阈值；
- SQL-shaped text 检查；
- 答案泄露检查。





代码默认 LLM_TEACHING_ENABLED=false。因此论文中要区分：

- LLM adapter 已实现；
- LLM 在线调用需要 provider、key、model 和阶段开关；
- 没有在线配置时由确定性反馈完成闭环。
