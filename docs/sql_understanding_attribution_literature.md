# Student Code 相关论文对 SQL 理解级归因的启发

本文整理若干 student code 自动反馈、提示生成、误解识别相关论文，并分析其对 SQL 教学系统中“理解级归因”的启发。核心问题是：系统不应只判断学生 SQL 与标准答案在字符串或知识点层面的差异，还应进一步推断学生对题目语义、Schema 字段、查询目标和结果粒度的理解偏差。

## 对 SQL 理解级归因的总体启发

这些论文共同说明，教学系统不应只关注学生提交与标准答案之间的表面差异，而应尝试恢复学生正在解决的“错误问题”。

对于 SQL 教学系统而言，理解级归因可以定义为：

> 学生 SQL 所体现出的错误任务模型。

也就是说，系统不仅要知道学生少写了 `WHERE`、写错了 `JOIN`、漏掉了 `GROUP BY`，还要进一步判断这些局部错误是否共同指向某种更高层的理解偏差。

例如，题目要求：

> 查询每个学生选修的课程数量。

如果学生 SQL 按课程分组，并输出课程名称，那么底层错误可能包括：

- 输出字段错误；
- `GROUP BY` 字段错误；
- 聚合粒度错误；
- 查询目标实体错误。

但理解级归因不应把这些作为多个零散错误输出，而应聚合为一个核心偏差：

> 学生将题目理解成了“每门课程有多少学生”，而不是“每个学生选修了多少课程”。



## 可迁移到系统中的机制



### 1. 构建 Misconception Library

可以为 SQL 设计一个理解偏差库，每个理解偏差包含以下信息：

```json
{
  "id": "wrong_result_grain",
  "name": "结果粒度理解错误",
  "description": "学生没有理解题目要求一行结果代表什么",
  "related_knowledge": ["GROUP BY", "aggregation", "SELECT"],
  "evidence_patterns": [
    "GROUP BY 字段与标准答案不同",
    "SELECT 输出实体与题目目标实体不同",
    "聚合结果数量级异常"
  ],
  "diagnostic_data_tactic": "generate_multiple_rows_per_entity",
  "hint_strategy": "先解释题目的一行代表什么，再提示应该围绕哪个实体分组"
}
```



### 2. 使用 Conceptual Mutants 表示常见误解

可以为每类理解偏差构造对应的错误 SQL 变体。


| 理解偏差                 | 概念 mutant 示例                         |
| -------------------- | ------------------------------------ |
| 忘记限定“已完成订单”          | 删除 `WHERE status = 'completed'`      |
| 将“每个用户统计”误解为“每条订单统计” | 去掉 `GROUP BY user_id` 或按订单字段分组       |
| 不理解无记录实体也要显示         | 将 `LEFT JOIN` 替换为 `INNER JOIN`       |
| 不理解去重计数              | 将 `COUNT(DISTINCT x)` 替换为 `COUNT(x)` |
| 混淆主查询对象              | 将标准答案中的主表替换为相关但错误的实体表                |


学生 SQL 越接近某个 conceptual mutant，就越说明该理解偏差可能存在。

### 3. 使用动态造数验证理解偏差

动态造数不应只用于判断学生 SQL 和标准 SQL 是否等价，还可以用于验证候选理解偏差。

例如：

- 如果怀疑学生不理解 `LEFT JOIN`，就生成没有匹配记录的实体；
- 如果怀疑学生不理解 `DISTINCT`，就生成重复关联数据；
- 如果怀疑学生结果粒度错误，就生成一个实体对应多条明细记录；
- 如果怀疑学生漏掉筛选条件，就生成满足和不满足条件的对照数据。

这样，理解级归因就不再依赖 LLM 的主观判断，而是有执行证据支持。

### 4. 将零散错误聚合为理解偏差

系统可以先得到底层错误：

```text
SELECT 字段错误
GROUP BY 字段错误
聚合结果不一致
输出行数异常
```

然后通过 misconception 规则聚合为：

```text
结果粒度理解错误
```

最终反馈给学生时，不应直接输出多个零散错误，而应先解释核心理解偏差：

> 你当前的查询更像是在回答“每门课程有多少学生”，但题目要求的是“每个学生选修了多少课程”。关键是先确定结果中一行代表什么：这里一行应该对应一个学生，而不是一门课程。



## 建议的系统流程

```text
学生 SQL
  -> AST 差异分析
  -> 知识点错误识别
  -> 映射到题目语义槽位
  -> 触发候选 misconception
  -> 动态造数验证
  -> 聚合零散错误
  -> 输出理解级归因
  -> 选择分层 hint
```

其中，LLM 不应直接作为最终裁判，而应作为辅助模块：

- 辅助生成题目语义槽位；
- 辅助总结多个错误之间的关系；
- 辅助生成自然语言 hint；
- 辅助在低置信度情况下提出追问。

最终归因仍应由结构证据、Schema 映射、SQL 差异、动态执行结果和历史错误模式共同决定。

## 小结

student code 相关论文给 SQL 理解级归因的核心启发是：

> 不要从“学生 SQL 哪里和标准答案不一样”直接跳到提示生成；  
> 应先推断学生可能正在回答哪个错误的问题，再用结构证据和动态反例验证这个推断，最后根据理解偏差生成分层提示。

因此，SQL 理解级归因的目标不是让 LLM 猜测学生心理，而是通过可验证的证据恢复学生的错误任务模型。
