## 三、当前能力逐项账本：真实实现、证据和欠缺



### 3.0 阅读口径

本节不再使用含义模糊的“已完成/部分完成”。每项能力按下列四种口径描述：


| 口径          | 含义                                             |
| ----------- | ---------------------------------------------- |
| **闭环实证**    | 在声明的数据、方言和资源边界内，结构识别、造数、执行、反例、变异/归因和路由均有真实运行证据 |
| **有界实现**    | 代码与契约测试已存在，但只覆盖明确的 SQL 形状、作用域或执行环境             |
| **仅识别/执行**  | 能解析结构或在原生引擎执行，不代表能构造反例、定位原子错因或更新学习状态           |
| **尚未实现/验证** | 当前没有对应机制，或只有设计，没有真实学生/原生环境/统计证据                |


最重要的能力边界是：**识别结构 ≠ 证明语义错误 ≠ 证明具体错因 ≠ 能安全教学归因**。后续各阶段只有在上游证据满足门槛时才继续。

- [PostgreSQL 原生教学审计](../data_construct_test/outputs/real_teaching_scenario_audit_pg_native_20260827_v3.json) 补充了 `cd.*`、CASE、窗口、DISTINCT、UNION、递归 CTE 等 6 个有界真实场景；窗口场景能判定但因无安全技能映射而不更新 Phase3。

### 3.2 Phase2：错因诊断、路径 bundling 与认知归因



#### 3.2.1 Phase2 是否识别等价性

Phase2 **不独立判定 SQL 等价**。它只消费 Phase1 的权威 rich verdict：


| Phase1 状态                                          | Phase2 行为                               | 是否允许认知归因/学习更新                |
| -------------------------------------------------- | --------------------------------------- | ---------------------------- |
| `SUPPORTED + NOT_EQUIVALENT + WRONG`               | 进入 20-rule 诊断、因果 bundling 和 witness/QSS | 只有强证据候选可以继续                  |
| `SUPPORTED + NO_COUNTEREXAMPLE_FOUND + CORRECT`    | 生成 operationally accepted 正确包           | 只有权威 Q-matrix 可产生正观测；不宣称全局等价 |
| `UNDECIDED`                                        | 返回未决，不写“你错在……”                          | 否                            |
| `ENGINE_GAP/INPUT_GAP/KNOWN_GAP/SEMANTIC_BOUNDARY` | 返回平台或能力边界                               | 否                            |
| syntax/safety                                      | 专用出口                                    | 不进入语义规则和 BKT                 |




#### 3.2.3 Phase2 的 LLM 已经如何参与

Phase2 现在不是“确定性诊断和 LLM 二选一”，而是“确定性证据先形成安全候选，LLM 在候选集合内复核”。当 `LLM_TEACHING_ENABLED=true`、模型 key 和模型名均存在时，路由会把以下内容交给 OpenAI-compatible provider：题目描述、标准/学生 SQL（仅内部复核）、方言/schema 摘要、Phase1 的结构差分、结果/变异摘要、witness 摘要、现有 rule candidate 和可用 evidence ID。

模型只能返回严格 JSON：`SUPPORTED_WRONG`、`OPERATIONALLY_EQUIVALENT` 或 `UNDECIDED`，并且必须引用已有 strong candidate/evidence。系统硬性拒绝：改写 Phase1 verdict、捏造 rule/skill/evidence、选择弱候选、输出 SQL/谓词/行值，或把不确定结果强行变成错误。通过校验后，模型最多影响两个地方：在已有强候选中选择教学主候选，以及润色前两段诊断叙述；模型 rationale 保存在私有 teaching audit snapshot，不进入学生响应。Phase1 verdict、Phase3 观测准入和 BKT 更新仍由确定性代码控制。

当前已有 provider mock contract、恶意 verdict/candidate/evidence、超时/格式错误和路由审计测试；尚未以当前真实 provider 做在线质量/成本/延迟 gate。因此应声称“LLM 接入与安全边界已实现”，不能声称“LLM 诊断效果已验证”。

#### 3.2.2 作用域与“沿路径划分错误点”的真实能力

系统先构建 `ScopedQueryGraph`，而不是把整条 SQL 压成一条平坦链。它保留 ROOT、CTE、DERIVED、SUBQUERY、SET/SET_BRANCH 等 scope，以及 `CTE_FEEDS`、`SUBQUERY_OF`、`CORRELATED_TO`、`SET_MEMBER_OF`、`LATERAL_TO` 等 composition edge。每个可配对 scope 内再按 14 个逻辑阶段排序：

```text
PRECHECK → CTE_PRODUCER → SOURCE_JOIN → ROW_FILTER → GROUP_AGG
→ GROUP_FILTER → WINDOW → QUALIFY → PROJECTION → DISTINCT
→ SET_OP → ROOT_ORDER → PAGINATION → EXTENSION
```

对学生展示时折叠为 S1 来源/连接、S2 行过滤、S3 分组粒度、S4 组过滤、S5 计算/投影/集合、S6 排序/截断。每个 diff 同时保存 scope、logical stage、teaching stage、`diff_id/obligation_id/mutation_test_id`，因此能形成“哪个 query block 的哪个逻辑阶段发生了什么差异”的有序集合。作用域无法可靠配对时，系统保留 unscoped/partial，而不是错绑到 root。

#### 3.2.3 已真实实现的 20 类错因识别


| 阶段  | rule                        | 具体识别内容                              | 升级为可靠候选所需的主要证据                                          |
| --- | --------------------------- | ----------------------------------- | ------------------------------------------------------- |
| S1  | `S1_MISSING_BRIDGE`         | 题目实体之间缺少声明的桥表/关系路径                  | join/source diff + authoritative FK bridge 或因果 witness  |
| S1  | `S1_CARTESIAN_PRODUCT`      | 多来源缺少有效连接约束导致笛卡尔积                   | missing ON/constraint + multiplicity witness            |
| S1  | `S1_OUTER_JOIN_MISUSE`      | INNER/LEFT/RIGHT 的保留侧语义错误           | join type diff + unmatched/dangling row witness         |
| S1  | `S1_SUBQUERY_CARDINALITY`   | 把集合子查询当单值，或比较形状与基数不匹配               | scalar/set shape + multi-row/engine/repair evidence     |
| S2  | `S2_BOUNDARY`               | `>`/`>=`、`<`/`<=` 等开闭边界错误           | comparison diff + boundary row                          |
| S2  | `S2_BOOLEAN_LOGIC`          | AND/OR、括号和优先级组合改变条件覆盖范围             | typed boolean-tree diff + distinguishing truth path     |
| S2  | `S2_NULL_LOGIC`             | `IS NULL`、NOT IN、比较 NULL 等三值逻辑错误    | null-sensitive diff + NULL/non-NULL witness             |
| S2  | `S2_AGGREGATE_IN_WHERE`     | 聚合值在行过滤阶段被使用                        | aggregate placement diff 或可信 execution error            |
| S3  | `S3_GRAIN_ENTITY_MISMATCH`  | 当前一行代表的业务实体与题意不一致                   | group diff + schema/cardinality/intent-bound evidence   |
| S3  | `S3_GROUP_KEY_MISSING`      | 分组维度过粗，缺少定义结果粒度的 key                | coarse-grain diff + merged-group result evidence        |
| S3  | `S3_GROUP_KEY_REDUNDANT`    | 多余维度把同一业务实体拆成多个组                    | fine-grain diff + split-group witness                   |
| S4  | `S4_HAVING_MISSING`         | 形成聚合后漏掉组级条件                         | HAVING diff + group witness                             |
| S4  | `S4_AGG_BOUNDARY`           | HAVING 聚合阈值的开闭边界错误                  | aggregate comparison diff + threshold group             |
| S4  | `S4_ROW_FILTER_IN_HAVING`   | 可逐行判断的同一条件被后置到 HAVING               | 同 scope、同 predicate 的 WHERE/HAVING relocation pair      |
| S5  | `S5_FANOUT_AGGREGATE`       | JOIN 倍增明细导致 SUM/COUNT 等虚高           | join multiplicity + aggregate delta/FK fan-out evidence |
| S5  | `S5_COUNT_NULL_SENSITIVITY` | `COUNT(*)` 与 `COUNT(column)` 统计对象不同 | COUNT shape + nullable schema + NULL witness            |
| S5  | `S5_CASE_INCOMPLETE`        | CASE 分支或 ELSE 覆盖不全                  | CASE diff + uncovered branch row                        |
| S5  | `S5_TOP_LEVEL_DEDUP`        | 最终结果漏去重或集合 ALL/DISTINCT 形状不当        | DISTINCT/set diff + duplicate output witness            |
| S6  | `S6_TOPN_WITHOUT_ORDER`     | 在未建立确定总序前截断结果                       | LIMIT/TOP/FETCH + 缺失/不完整 ORDER                          |
| S6  | `S6_ORDER_OFFSET`           | 排序方向、tie-breaker 或 offset/cutoff 错位 | order/offset diff + cutoff witness                      |


这 20 条的三态矩阵不是只测“能命中”：每条都测试“充分原子证据应命中”“邻近错因不能误标”“只有结构信号但证据不足必须 unresolved”。当前 [Phase2 acceptance](../data_construct_test/outputs/phase2_acceptance_report.json) 为 7/7 组、169/169 测试通过。

#### 3.2.4 Fault bundling、错误集合和最早偏离点

真实算法分两趟：

1. 扫描所有 scope 和所有阶段，生成候选；不会因为 S1 命中就停止，因此独立的 S6 错误仍可保留。
2. 按 `(scope_id, rule_id)` 聚合共享 diff/obligation 的候选。
3. 只接受有 stable evidence 绑定的 `CAUSES/MASKS/RELOCATES_TO` 做抑制；`CO_OCCURS` 只能表示共现，不能制造因果。
4. 输出四个集合：`primary_fdp`、`secondary_roots`、`suppressed_symptoms`、`unresolved_candidates`。
5. 在 blocking causal roots 中，按 scope 顺序、逻辑阶段、证据等级、修复性、严重度和稳定 ID 选 `primary_fdp`。

所以系统当前能找到的是：**在已配对 query scope 和已验证因果根集合中的“首要教学偏离点”**。它不是数据库执行引擎的通用 tuple provenance，也不能在 scope partial、无 witness、只有 AST 差异或多个错误互相遮蔽时证明“语义上绝对最早”的错误；这类候选会进入 secondary 或 unresolved，而不会强行排序成唯一根因。

#### 3.2.5 当前“认知归因”能做到和不能做到的事


| 能做到                                                                     | 不能做到                                                                                  |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 把强证据错误映射到 20 个原子 SQL skill，例如 `S2_NULL_LOGIC → null.three_valued_logic` | 不能仅凭一次 SQL 判断学生是“不知道、概念混淆、粗心还是抄写失误”                                                   |
| 用 QSS 输出“当前行为—冲突/物证—苏格拉底式问题”                                            | 不能把模板式解释等同于经过教育实验验证的认知模型                                                              |
| 区分 primary、独立 secondary、dependent symptom、unresolved                    | 不能把阶段先后或 AST 距离当成心理因果                                                                 |
| 对高级差异保留 `UNCLASSIFIED_SUPPORTED_DIFF` 和证据，不错误套用最近的规则                    | 当前 20 条之外的 window frame、复杂 CTE/集合、alias/function/dialect 等没有完整 misconception taxonomy |




### 3.3 Phase3：可信学习更新与教学支架选择



#### 3.3.1 什么信息会更新，什么信息不会更新


| 提交情况                                 | 观测来源                         | 更新内容                                                                                             | 安全门槛                                                            |
| ------------------------------------ | ---------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------- |
| 正确提交                                 | 服务端 Q-matrix                 | 对 `PRIMARY + observable_on_correct=true` 且 provenance 为 `AUTHOR_DECLARED/GENERATED` 的 skill 写正观测 | 题目最多 8 skills、最多 3 primary；supporting/inferred/客户端伪造均不能授权更新     |
| 错误提交                                 | Phase2 rule→atomic skill map | 对 primary 和独立 secondary 中 `CAUSAL_VERIFIED/REPAIR_VERIFIED` 的 skill 写负观测                         | 只接受精确 Phase2/schema/rule 版本；display-only knowledge point 不是授权来源 |
| syntax/safety/undecided/platform gap | 无                            | 不更新                                                                                              | 不把平台失败或语法问题伪装成语义未掌握                                             |
| 正确但无 Q-matrix                        | 无                            | `SKIP_NO_ASSESSMENT_MAP`                                                                         | 不从标准 SQL 临时猜测技能                                                 |
| 弱证据或 advanced 无映射                    | 无                            | `NO_ELIGIBLE_OBSERVATION`/固定 skip reason                                                         | 识别到差异也不更新 BKT                                                   |
| 答案已揭示                                | 无                            | skip                                                                                             | 防止看过答案后的结果污染掌握度                                                 |


每个学习事件保存：`taxonomy_version`、`skill_id`、正/负结果、来源与版本、evidence grade、Phase2 candidate/rule、source role、logical stage、实际支架等级，以及 BKT 更新前后的数值。状态以 `(user_id, taxonomy_version, skill_id)` 分区，避免 broad curriculum skill 与 atomic skill 共用一个概率。

#### 3.3.2 BKT 当前具体更新什么

当前使用未校准四参数 BKT：`P(L0)=0.20`、`slip=0.10`、`guess=0.20`、`transition=0.10`。每次观测先保存 Bayes 后验 `posterior_mastery`，再保存学习转移后的 `next_prior`；下一次只读取 `next_prior`。状态还保存 observation count、参数版本和 state version；唯一键 `(submission_id, taxonomy_version, skill_id)` 防止重放重复更新。UI EMA 与 BKT 状态分离，不会二次平滑后再写回。

这证明的是“公式、来源和幂等闭环已经接通”，不是参数有效。当前仍为 `UNCALIBRATED_MVP`，没有真实学生轨迹支持 slip/guess/transition、支架权重或 mastery 阈值的教育学解释。

#### 3.3.3 如何选择本轮教学目标和支架深度


| 决策       | 当前已实现策略                                                                                                                                                      | 当前欠缺                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| 选哪个错误先教  | `FDP/PRIMARY` 是不可被分数越过的硬层级；其后最多加入一个 independent secondary；suppressed/unresolved 永不选                                                                          | priority 权重是工程初值，尚未用学习收益校准；Phase4 实际每轮仍只展示一个 selected target                          |
| 同层候选排序   | `0.30*instructional_impact + 0.25*recurrence + 0.20*mastery_deficit + 0.15*question_alignment + 0.10*evidence_strength`                                      | `instructional_impact` 和各权重不是心理测量结果                                                   |
| 本次提示深度   | `support_need = 0.35*(1-mastery) + 0.30*failure_streak + 0.10*recent_hint_ratio + 0.10*behavioral_support_need - 0.15*recent_unassisted_success`，裁剪到 `[0,1]` | 提交前提示暴露尚未完整记录，所以 `recent_unassisted_success` 当前保守为 0；behavioral need 只是事件代理，不是疲劳/认知负荷 |
| L1–L4 划分 | `[0,.25)→L1`、`[.25,.50)→L2`、`[.50,.75)→L3`、`[.75,1]→L4`                                                                                                      | 阈值未校准；当前只能说四档在路由中可达，不能说是最优剂量                                                          |
| 下一题难度    | `challenge_index` 单独由 mastery、无辅助成功和行为支持代理计算，只用于下一题                                                                                                          | 当前没有完整的自动选题器和经验证难度模型；不得拿它决定当前 hint 深度                                                 |


连续相同可信错误的现有工程行为可从 L2 提升到 L3、L4，推荐等级、实际等级、BKT 事件和教学审计会保持一致。但 broad↔atomic skill 桥接、题目 revision fingerprint、真实行为校准和跨课程迁移仍未完成。

### 3.4 Phase4：把选中的错因落实为教学支架

Phase4 不重新判题、不重排错误、不读取标准 SQL。它只消费 Phase3 已绑定的一个 `selected_target`，并核对 `candidate_id/rule_id/skill_id/taxonomy/stage/source role/evidence grade` provenance 后生成动作。


| 支架等级 | 当前实际交付内容                                | 教学意图               | 真实边界                                     |
| ---- | --------------------------------------- | ------------------ | ---------------------------------------- |
| L1   | 一个与首要错因绑定的苏格拉底式自查问题                     | 促使学生先自行检查概念        | 没有可信 target 时只能给通用流程问题，不是假装个性化           |
| L2   | “当前查询行为” + 自查问题                         | 让学生先理解自己的 SQL 做了什么 | 不提供物证或修复方向                               |
| L3   | 当前行为 + 最小冲突/物证 + 自查问题                   | 用真实反例打破错误心智模型      | witness 不可安全绑定时必须降级，不能编造数据               |
| L4   | 当前行为 + 物证 + rule-specific 概念检查方向 + 自查问题 | 给出解决原则，但仍让学生完成 SQL | 20 条规则有版本化 reflection；只给概念检查步骤，不生成完整 SQL |


当前能称为“使用正确支架”的含义是：支架与已验证 rule、选中 target 和推荐深度一致，并且只展示一个焦点错误。它还没有通过真实学生实验证明“这个支架一定最有效”，也没有实现学生回答苏格拉底问题后的多轮理解判断、按回答动态换支架、自动生成相似练习或教师人工干预策略。

正确提交、syntax、安全拦截和无可信 target 不伪造自适应教学；Phase4/5 任一步失败都保留权威 verdict，并 fail-closed 到可审计 L1。

### 3.5 Phase5：启发性自然语言与答案防泄漏



#### 3.5.1 当前真实语言能力


| 能力     | 当前实现                                                                                                                 | 不能扩大声称的部分                                                            |
| ------ | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 自然语言反馈 | `zh-CN/zh-TW/en` 三种确定性模板；按“当前行为、冲突与物证、修改前检查方向、请思考”分段；L2-L4 可由 LLM 对已批准片段做一对一润色                                       | 语言质量、语气适配和长对话连贯性尚未通过真实教师/学生盲评；L1、正确接受、安全/语法通知仍固定本地模板                 |
| 教导与启发  | 20 条规则各有概念级 reflection 和苏格拉底式问题；不直接给替换 SQL                                                                           | 这是教学设计上的“启发式结构”，尚无教师评分、学生理解度、学习增益或 A/B 证据证明其启发效果                     |
| 个性化    | 根据选中错因、mastery/failure/hint history 调整 L1–L4 深度                                                                      | 除目标和深度外，尚未根据语言水平、常见误解类型、阅读能力或历史自然语言回答改写内容                            |
| 确定性与审计 | 同一 deterministic action plan 字节级稳定；LLM 输出必须通过 action_id 一一对应、固定动作不变、SQL-shaped 文本拒绝和最终答案片段扫描；保存内容 digest、实际等级、来源和降级码 | LLM 路径不是字节确定的；通过模型版本、策略版本、digest 和失败回退保持可审计，但仍需离线 replay、模型漂移和人工质量评估 |




#### 3.5.2 当前防泄漏机制

1. Phase5 的 LLM 只接收 Phase4 已批准的 action 文本、动作类型、语言和实际等级；不读取 `correct_sql`、标准 AST、mutation SQL 或完整 witness database。固定动作（问题、接受、安全/语法通知）不能被模型改写。
2. 新提交学生响应中的完整 `diagnostic_package` 固定为 `null`，避免 L1/L2 绕过裁剪直接看到 primary/secondary/witness/QSS。
3. 公共诊断包递归拒绝 `answer_sql/correct_sql/standard_sql/reference_sql/replacement_sql/mutation_sql/test_database/raw_observation` 等字段。
4. 最终反馈对标准 SQL 全文和 `SELECT/WHERE/GROUP BY/HAVING/ORDER BY/LIMIT/OFFSET` 等抽取片段做归一化泄漏扫描；命中则拒绝。
5. LLM 超时、provider 错误、JSON 结构错误、动作错配、语义锚定不足或泄漏校验失败时，先回退 deterministic safe renderer；主渲染/最终安全校验本身失败时，再使用独立本地 emergency renderer 降为不含答案的 L1，并记录 `OVERRIDDEN/FALLBACK`；BKT 只记录实际交付等级。
6. 学生可见 `teaching_support` 只含推荐/实际等级和策略版本，不含 rule、skill、candidate、observation、Q-matrix 或 witness。

因此当前有真实证据支持的是“在现有确定性模板、LLM 输出门禁和已覆盖攻击形状下不泄漏”：PG 原生 16 个路由分支和 MySQL 原生 14 个路由分支的 learner-safe rate 均为 1.0；LLM 具体生成质量目前只有 mock contract，尚无在线 provider 质量结论。它还不是形式化 non-interference 证明；标准答案的同义改写、编码/Unicode 混淆、模型间接提示、客户端旁路字段和红队攻击仍需单独的 adversarial leakage suite 与人工审查。

### 3.6 按阶段列出的具体剩余工作

## 四、论文故事：建议采用的主线



### 4.1 论文类型和一句话定位

建议把论文定位为“新的教学诊断问题设定 + 一个证据驱动的系统机制”，而不是泛泛的“LLM SQL tutor”：

> 给定题目意图、标准 SQL、学生 SQL 和不完整/无实例数据的 Schema，系统如何在不泄漏答案的前提下，区分结构差异与真实语义错误，自动构造最小反例、定位最早可解释错因，并把强证据安全地转成分层教学反馈和可更新的学习状态？

可以使用一个暂定工作名，例如 **Evidence-Grounded SQL Teaching Loop**；正式命名应等实验结果稳定后再定。论文的核心不是“用了多少模块”，而是把 SQL 教学中的判题、证据生成、因果诊断和反馈控制统一成一个有边界的闭环问题。

### 4.2 Introduction 的压缩故事

1. **场景/痛点**：学生提交的 SQL 经常“能解析、能执行，但语义错”。例如把 `>` 写成 `>=`，把 `LEFT JOIN` 写成 `INNER JOIN`，或在 CASE 中把 member 分支写成 guest 分支。普通 OJ 只能给 Wrong Answer，教师却需要解释“哪一步查询思路偏了”。
2. **现有方法的三个局限**：
  - 只看语法或 AST：结构不同可能仍等价，结构相同也可能在边界数据上错误；不能处理 `IN/EXISTS/JOIN`、函数依赖和方言语义。
  - 只跑随机/固定数据：很多错误只在临界值、NULL、重复、未匹配连接或分组粒度变化时显现；没有 witness 时，系统无法给出可靠诊断。
  - 只让 LLM 解释或直接修复：可能混淆根因与伴随现象，反馈不稳定、泄漏答案，也不能把一次解释可靠地写成学生知识状态。
3. **问题本质**：SQL 语义诊断是一个多证据、带 schema/方言/资源约束的部分函数问题；“未判定”与“错误”必须分开，有限 witness 能证明观察到的差异，但不能宣称所有数据库上的形式等价。
4. **Our Goal / Problem Formulation**：对查询对 `⟨q_correct, q_student, S, Q⟩`，在声明的结构域、作用域和执行后端内，输出 `verdict + evidence + root diagnosis + learner-safe action`；若 schema、witness、方言或资源条件不足，显式输出 boundary/skip，而不是猜测。
5. **Key Idea**：把 AST/IR 候选差异、SchemaCatalog 约束、obligation-driven witness、真实引擎执行和 mutation repair 组成一个证据链；再按教学逻辑路径做 FDP bundling，只把强因果 rule 投影成 atomic skill，最后由确定性教学策略渲染反馈。
6. **关键挑战**：语义等价与结构差异的错位；如何定向造出最小且不互相覆盖的反例；如何在证据不充分时既不误诊又能给学生可用反馈。
7. **方法总览**：Phase1 采证据，Phase2 诊断与打包，Phase3 可信观测/调度/BKT，Phase4–5 选择并渲染支架，Phase6 以幂等事务保存提交、审计和状态。
8. **贡献收束**：提出问题设定与边界契约；实现多证据 witness/mutation 机制；实现作用域感知、答案安全的教学闭环；在 SQLite compatibility 与 PostgreSQL/MySQL 原生目标上报告可复核的有界实测，并明确未完成的教学校准。



### 4.3 方法部分的层次


| 方法层       | 解决什么                          | 关键对象                                                                               | 论文中应强调的性质                        |
| --------- | ----------------------------- | ---------------------------------------------------------------------------------- | -------------------------------- |
| 统一表示与边界   | 让结构差异、schema scope、方言和执行状态可区分 | CFG/IR、ASTDiff、SchemaCatalog、Scope、Backend                                         | 解析/作用域/执行分层；不把 parser 能识别写成可执行支持 |
| 证据生成      | 把“可能错”变成可观察差异                 | TacticRegistry、Obligation、WitnessWorld、NULL/边界/连接/分组策略                             | 定向、可审计、资源有界；输出最小差集而非随机大数据库       |
| 语义判定与因果隔离 | 区分错误、有限等价和未决，并定位根因            | native/SQLite executor、ordered compare、Mutation Evidence                           | 原生引擎必须显式标记；修复后等价才提升因果证据等级        |
| 查询路径诊断    | 降低多错误反馈的认知负荷                  | S1–S6 pipeline、FDP、secondary/suppressed/unresolved、QSS                             | 先反馈最早高置信偏离，不平铺下游连带错误             |

| 持久化与复现    | 让教学闭环能重放且不重复更新                | attempt_id、request fingerprint、submission/audit/behavior/state                     | 同一提交重放不重复跑 Phase1、不重复写 BKT/对话    |




### 4.4 贡献点的建议写法

建议最终写成 3–4 条，避免把每个工程模块都包装成独立创新：

1. **问题与契约**：形式化无固定实例、带 Schema/方言/资源边界的 SQL 教学语义诊断任务，并定义 `INPUT_GAP / ENGINE_GAP / UNDECIDED / NOT_EQUIVALENT` 等不确定性分流。
2. **证据驱动诊断机制**：提出由结构差分、schema-aware witness、原生执行和 mutation repair 组成的多证据链，能够把有限反例与候选错因绑定，而不是只依赖 AST 或随机数据。
3. **教学安全闭环**：提出作用域感知的 Query Path/FDP bundling 和强证据 rule→atomic skill→分层反馈链，在不把内部诊断包/参考答案暴露给学生的前提下维护可审计学习状态。
4. **系统性评估**：在明确的 SQLite compatibility、PostgreSQL 16、MySQL 8.0.46 边界下，报告结构/数据/mutation/归因/路由证据，并用输入 gap、witness gap、engine gap 和 calibration gap 报告系统尚未覆盖的部分。

## 六、论文中必须主动写出的边界和威胁

这些不是削弱论文，而是避免审稿人用一个过大的 claim 推翻全部工作：

- 有限 witness 可以证明“在该 witness 上观察到差异”，不能证明任意数据库实例上的全局等价。
- SQLite compatibility 不能作为 PostgreSQL/MySQL 语义证据；native report 必须单独记账，并注明目标版本、driver 和 identifier mode。
- schema/catalog 不完整、题目 SQL 在目标方言下无效、结果超过资源上限，都应分类为 boundary/input/engine，而不是强行判断学生错误。
- Phase2 20 条是 frozen MVP rule，不是所有 SQL misconception；窗口、复杂递归/集合和未绑定的高级形状应安全 skip。
- BKT 参数和支架权重尚未用真实学生轨迹校准；当前只能声称“原始 BKT 工程闭环可运行”，不能声称已经测量学习能力或认知负荷。
- 当前生产权威仍是 Phase1/Phase3/Phase4 的确定性路径；LLM 已作为 Phase2 证据复核和 Phase5 文案润色的可选受限组件接入，不能改变 verdict、target、support level，也不能替代 deterministic fallback。
- 旧文档中的“伪 A*”“单一 lambda”“18 条全覆盖规则”等表述已被当前实现修订为 ConstrainedPriorityScheduler、support/challenge 分轴和 20 条 MVP rule，论文应只使用新口径。



## 七、当前最合理的论文推进顺序

1. 冻结一份不含 hidden 明文的公开实验快照，分开记录 compatibility、PG native、MySQL native 和输入/engine gaps。
2. 完成真实学生提交的匿名化、标注协议和 train/validation/test split；先做 RQ1/RQ3 的离线诊断实验。
3. 完成 BKT calibration artifact 和小规模 A/B 用户实验；若样本不足，只报告 pilot，不把 `UNCALIBRATED_MVP` 改名。
4. 补精确 `mysql:8.0.46` Docker 复现及 T-SQL/Oracle 的最小 live gate；把 Docker/driver/session 版本写入实验表。
5. 对 LLM 路径做真实 provider 的固定版本 replay，记录模型、提示策略版本、延迟、token/cost、接受率、回退率和泄漏红队结果；再定论文标题、图表和贡献措辞。主图建议只画一条主链：`student SQL → evidence → witness/native execution → causal diagnosis → safe adaptive feedback (LLM wording under gates)`，其余细节放方法图和附录。
