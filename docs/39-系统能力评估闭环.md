# SQL 教学系统能力评估闭环

本文件定义统一评估口径。它不改变 Phase1--Phase6 的运行契约，只规定如何把各阶段已有的机器报告合成为一份可复核的能力账本。

## 阶段与能力问题

| 阶段 | 要回答的问题 | 核心证据 |
|---|---|---|
| Phase0 数据与来源 | SQL、schema、来源和版本是否可追溯 | enriched corpus 的 source id/url/hash/schema catalog |
| Phase1 结构与判定 | CFG/ASTDiff、造数、执行、等价性、变异和归因是否闭合 | identity、mutation、fuzzer、database profiles |
| Phase2 诊断 | 每个 rule 是否有合法 scope、证据等级和矩阵覆盖 | acceptance guard、rule catalog、scope graph |
| Phase3 学习 | 正观测是否只来自 Q-matrix，负观测是否来自强因果 rule，BKT 是否幂等 | full-chain route、learning events、state counts |
| Phase4 教学动作 | primary/FDP 是否优先，支架预算和 suppression 是否生效 | teaching action contract、route branch |
| Phase5 反馈 | 只渲染 learner-safe 内容，正确/语法错/安全拦截走正确分支 | safe output、diagnostic redaction |
| Phase6 审计与持久化 | submission、teaching audit、行为事件是否可追溯且重放不重复写入 | persistence counts、idempotency、audit invariants |

## 指标规则

- 每个经验指标都保存 `successes`、`trials`、`rate` 和 Wilson 95% 区间；分母写入 `denominator_policy`。
- `INPUT_SCHEMA` 表示外部题目/schema 自身不能在权威 catalog 中解析；它会进入 Phase0 和失败登记，但不被伪装成判题引擎能力。
- `BACKEND_BOUNDARY` 表示当前 SQLite compatibility 或明确未承诺的方言能力；它不计为支持。
- `WITNESS_NO_COUNTEREXAMPLE` 表示标准/学生 SQL 在当前造数下没有被区分，属于造数能力缺口，不得写成“学生正确”。
- `MUTATION_EVIDENCE_GAP` 表示结果可能已经不同，但变异修复或归因没有闭合。
- 经验指标点估计达到门槛但样本不足或 Wilson 下界未达到门槛时为 `WARN`；契约型单元断言则使用 `statistical_gate=false`。
- SQLite 兼容运行只证明当前有界转换与 SQLite 执行结果，不证明原生 MySQL、PostgreSQL、T-SQL 或 Oracle 的全部语义。

## 评估门禁

| 能力板块 | 主要指标 | 通过线 |
|---|---|---:|
| Phase0 来源 | provenance、schema catalog、必需证据完整性 | 100% |
| Phase1 identity | structure、data、mutation、attribution、full flow | 99%、95%、90%、90%、95% |
| Phase1 mutation | counterexample detection、mutation execution、attribution | 90%、95%、90% |
| Phase2 诊断 | 7 组 acceptance、169 个测试、20/20 rule matrix | 100% |
| Phase3 学习 | Q-matrix 正观测、Phase2 原子负观测、无映射跳过、BKT 幂等 | 契约断言 100% |
| Phase4–6 | primary/FDP 教学动作、learner-safe 反馈、审计和重放幂等 | 契约断言 100% |

所有经验比例保存 Wilson 95% 区间；点估计达到门槛但区间下界不足时为 `WARN`。闭合评估还要求 7 个输入件全部存在：corpus、identity 汇总及 ledger、mutation 汇总及 ledger、Phase2 报告、真实 full-chain 报告。缺件直接是 `PHASE0_SOURCE/FAIL`，不能只因为其他阶段有结果就宣称闭合。

## 当前运行方式

先运行外部 corpus 的 Phase1 综合审计、1,000 条参数化生成回归、已有 430 条 bounded fuzzer、database profiles、Phase2 acceptance 和真实 API route audit，再组合报告。综合报告必须带 `web_corpus_identity` / `web_corpus_mutation` 的 `origin` 和逐案失败 ledger；评估器也兼容旧的 identity/mutation 双报告：

```bash
python data_construct_test/scripts/run_system_capability_evaluation.py \
  --corpus data_construct_test/outputs/external_enterprise_sql_corpus_enriched_20260826.jsonl \
  --phase1-report data_construct_test/outputs/phase1_external_convergence_20260826_v5.json \
  --phase1-failures data_construct_test/outputs/phase1_external_convergence_20260826_v5_failures.jsonl \
  --large data_construct_test/outputs/phase1_large_convergence_20260826_v4.json \
  --fuzzer data_construct_test/outputs/e2e_robustness_fuzzer_report.json \
  --profiles data_construct_test/outputs/phase1_cfg_database_profiles_report.json \
  --phase2 data_construct_test/outputs/phase2_acceptance_report.json \
  --full-chain data_construct_test/outputs/new_web_full_chain_audit_20260826_final_v3.json \
  --output data_construct_test/outputs/system_capability_evaluation_20260826_final_v4.json
```

报告同时输出 JSON 和 Markdown。任何阶段的 `FAIL` 都会使总状态为 `FAIL`；这表示仍有需要修复或补充证据的能力，不表示系统整体不可用。

## 2026-08-26 最新复测

- Phase0：119/119 条外部记录有来源和 schema catalog，7/7 个必需证据件齐全。
- Phase1 大样本：1,117 个有效 case（1,000 个参数化生成 + 117 条外部 identity）结构、数据、mutation、归因、full flow 均为 1,117/1,117；另有 2 条外部输入 schema gap。
- 外部 identity：117/117 可测样本闭合；2 条被保留在失败 ledger 中，未计入引擎分母。
- 外部 mutation：77 个排除输入 schema gap 的负变异中，50/77 产生真实数据反例，77/77 完成 mutation execution，57/77 完成隔离修复证据，59/77 完成归因；27 条归类为 `WITNESS_NO_COUNTEREXAMPLE`，另有 1 条输入 schema gap，没有 unexpected engine failure。这一板块当前仍未达到教学级 90% 证据门槛，因此总评为 `FAIL`，不能把“执行了但数据未区分”当成学生正确。
- 既有 Phase1 防回归：430/430 bounded fuzzer 通过；8,832 次 database-profile execution 无执行错误，100/100 负例被检测。
- Phase2：7/7 acceptance group、170/170 测试通过，规则目录与 20/20 matrix 精确匹配。
- Phase3–Phase6：真实 API route audit 通过；5 次提交、2 条学习观测、1 个 skill state、2 条行为事件、5 条 teaching audit、15 条消息，Q-matrix/无映射/语法错/安全拦截/重放分支均通过。

该次报告总评为 `FAIL` 的唯一实质来源是外部复杂 mutation 的 witness 证据不足（主要是 DISTINCT、比较边界和 UNION 在合成数据中没有产生反例），而不是发现了新的随机执行崩溃。外部语料还没有覆盖 `cte-recursive`、`except`、`intersect`、`subquery-exists` 标签；生成式回归已覆盖这些家族，但不能替代真实外部语料。当时原生 MySQL/PostgreSQL 语义尚未纳入该次报告，已在下方补充复测。

## 2026-08-27 原生 Docker 复测补充

- 修复了 learner-safe schema preview 对结构标识符的误删：`GROUP BY facid` 等题目引用的表/列名继续保留，数据单元仍按安全策略脱敏；未知 namespace 和 SQL-shaped identifier 仍 fail-closed。
- PostgreSQL 16 原生 runner 已可达。62 组 PGExercises 公开题对的 Phase1 CFG 收敛结果为 `62/62`，结构、数据、变异、归因和 full-flow 均为 `1.0`，无 witness gap、mutation gap 或 unexpected failure。
- PostgreSQL 原生 API 教学审计覆盖聚合边界、`cd.*` 限定名、CASE、窗口、DISTINCT、UNION、递归 CTE：identity `6/6`、选定变异 `6/6`、witness gap `0`、learner-safe `1.0`。CASE 与 UNION 在有强证据的具体形状下进入原子 skill；窗口的当前候选仍因没有安全的 Phase2 rule→atomic skill 映射而跳过学习更新。
- 这组原生结果只证明列出的公开样本和 PostgreSQL 16 runner；不能把旧外部综合报告中的 `FAIL` 自动改写为全局通过。MySQL 8.0.46 必须在锁定镜像实际启动并完成 live gate 后单独记账，不能用已有的 MySQL 8.4.6 容器替代。

## 2026-08-28 原生 MySQL 复测补充

- MySQL 原生 runner 已接入精确版本/标识符门禁：`mysql://...` 必须通过 MySQL `8.0.46` 与 Linux `lower_case_table_names=0` 检查；8.4.6 或大小写语义不一致的实例会 fail-closed。本次 live gate 使用同版本原生实例，`tests/test_native_engine_live_e2e.py -k mysql` 为 `7 passed`。
- MySQL 原生教学审计 `real_teaching_scenario_audit_mysql_native_20260828_v4.json` 为 `5/5` identity、`5/5` selected mutation、`0` witness gap、`1.0` learner-safe；14 个路由分支中 `CORRECT=6`、`WRONG=8`。Phase3 对过滤、NULL、HAVING、LEFT JOIN、EXISTS 均产生了可追溯的原子 skill 观测或安全跳过。
- LEFT JOIN 反例已被原生 MySQL 复现：标准查询返回两个匹配箱号以及一个右侧 NULL 扩展行，INNER JOIN 变异只返回两个匹配箱号；报告记录 `only_in_standard_sample=[[null]]`。CASE 场景中 `memid=0` 的 guest 分支与非零 member 分支使用不同成本，标准/变异聚合结果可区分，并进入 `S5_CASE_INCOMPLETE → projection.case_coverage`。
- 为兼容真实语料的原生装载，runner 保留 `CHAR/VARCHAR` 主键宽度、为无界文本键使用安全的有界回退类型，并将生成式整数/文本哨兵值确定性地适配到声明类型；MySQL 变异重放只恢复权威 catalog 中已知表/列的源大小写，不放宽未知标识符安全策略。
- 62 条 XD Deng 外部语料的初步 MySQL 原生运行中，26 条是源 SQL/schema 大小写或 catalog 输入 gap；4 条暴露了严格 `ONLY_FULL_GROUP_BY`、生成主键碰撞和结果上限边界，因此该基准不作为全量通过证据。它说明 native runner 已真正接入目标引擎，也说明外部语料不能在未经语义清洗时冒充 MySQL 通过。
